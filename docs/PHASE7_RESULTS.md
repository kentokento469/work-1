# Phase 7 — 汎用タスク管理システムの構築と業務管理基盤への統合

実施日：2026-10-16
環境：Node.js 22 / Chromium（Playwright 1.56）/ fake-indexeddb。「iPhone」は Chromium の iPhone 13 エミュレーション（実機では未検証）。

## 1. 実装前の調査（既存の Task モデル）

| 項目 | Phase 6 までの状態 | 一般のタスク管理としての問題 |
| --- | --- | --- |
| 担当部署 `assigneeDepartmentId` | 必須（型・検証・バックアップ検査） | 個人の作業や部署と無関係なタスクを登録できない |
| 期限 `dueDate` | 必須（作成時に7日後を自動入力） | 期限のないタスク（いつかやること）を表せない。自動の期限が誤った「期限超過」を生む |
| 生成元 `source` | manual / onboarding / inquiry / automation | 自動生成と手動が同じストアで管理されていた（この設計は維持） |
| 分類・構造 | なし | プロジェクト・タグ・サブタスク・チェックリスト・繰り返し・依存関係・カレンダー・ボードがない |

## 3. 設計上の判断

| 判断 | 理由 |
| --- | --- |
| 自動生成タスクと手動タスクを同じ `tasks` ストア・同じ `TaskService` で扱う | 別システムにすると一覧・通知・検索が二重になる。`source`・`ruleId`・`inquiryId`・`links` で発生元を識別し、元の画面へ戻れる |
| 新しい項目はすべて任意（旧データには存在しない＝未設定） | 既存タスクの書き換え（データ移行）を不要にし、移行失敗のリスクをなくす。DB v6 はプロジェクトのストアを追加するだけ |
| 繰り返しは「完了したときに次回を1件作る」方式 | ブラウザ内保存のため、アプリを閉じている間に生成されたように見せない。`nextOccurrenceId` で二重生成を防ぎ、長期間未完了でも過去分をまとめて作らない（今日以降の最初の回へ） |
| 次回期限は前回の期限＋基準日 `anchor` から計算 | 完了日基準だと期限がずれていく。31日・2/29 は存在しない月だけ月末に寄せ、翌回以降は元の日に戻す |
| チェックリストとサブタスクを分ける | 「小さな確認項目」と「担当・期限を持つ作業」は必要な情報量が違う。サブタスクは1段までに制限し、無制限の入れ子を作らない |
| プロジェクト削除はタスクを削除しない | 業務履歴を失わない。所属だけ外し、元に戻すと再び所属する |
| クイック追加の日付は「候補」として表示 | 誤認識による意図しない期限を防ぐ（外せる・名詞の「月末の〜」はタスク名に残す） |
| 通知・警告を自動でタスクにしない | 作業が必要な時だけ利用者が「関連タスク」から作成（重複を防ぐ） |
| 依存関係は任意・完了は妨げない | 基本操作を複雑にしない。前提未完了は表示で知らせる |

## 6. 残課題・制約

- 実機 iPhone Safari では未検証（カンバンの横スクロール、カレンダーのタップ、日付入力の操作感）
- 繰り返しの「完了日を基準にする」方式（例：完了から7日後）は未対応（期限基準のみ）。営業日・祝日の考慮は Phase 12
- ボードのドラッグ＆ドロップは PC のみ（スマホは進捗メニュー）。タッチのドラッグは実装していない
- タスクの担当者は自由入力（利用者・権限の概念は Phase 13〜14）
- 全件をメモリに読み込む方式のため、数万件規模の性能は Phase 12 で計測・改善する
