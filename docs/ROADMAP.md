# WorkCore 開発ロードマップ（2026-10-19 方針の再定義）

これまでの [Phase 8〜16 統合計画](PHASE8_16_PLAN.md) を、オーナーの方針の再定義（2026-10-19）に合わせて見直したもの。**以後はこの文書を正とする。**

## 0. 前提（最優先）

| 項目 | 内容 |
| --- | --- |
| 位置づけ | 個人の学習・実験・技術検証・開発練習のためのアプリ。企業での運用・商用化・販売・複数ユーザーへの提供は目的にしない |
| 利用者 | オーナー1人 |
| 構成 | GitHub Pages（公開）＋ IndexedDB など無料のローカル技術（保存）。**クラウドバックエンド（Supabase など）は導入しない** |
| 費用 | 外部の有料サービスは使わない。将来の有料化も想定しない |
| 判断基準 | 「実運用に必要か」ではなく「**学習・技術検証・完成度の向上に価値があるか**」。設計品質・操作性・処理性能・コード品質は高い水準を目指す |
| 実験 | 学習効果の高い技術は積極的に試す。ただし、実験のためだけの複雑さを恒久的に残さない（残すのは、効果を測って価値が確認できたものだけ） |
| データ | 既存の機能・保存データを壊さない。エクスポート/インポートによるバックアップは維持・改善する |
| 承認が必要な操作 | 費用の発生・外部アカウントの作成・外部への情報送信・既存データの破壊。それ以外の調査・実装・ローカルテストは自律的に進める |
| 設計の考え方 | 「メタ理解設計」「集合値から学ぶ」を継続（[META_DESIGN.md](META_DESIGN.md)）。操作回数・情報への到達性・処理速度・エラーからの復旧・操作の一貫性を重視 |

品質ゲート（各 Phase の完了条件）は従来どおり：型チェック・単体テスト・E2E（Chromium の2画面サイズ。WebKit は参考）・本番ビルド・改善前後の計測・未検証の項目の明記。

## 1. これまでの計画の分類

A：継続する（学習効果・操作性・性能・安定性の向上）／B：実験として残す（実運用には不要でも学ぶ価値がある）／C：中止する（複数ユーザー・商用・有料サービス・企業向けの本番インフラが前提）

## 2. 新しい開発の順序

性能の問題（今回の対応の残り）→ ローカルデータを守る仕組み → 保守性 → 操作性 → 実験、の順にする。性能と保守性を先にするのは、後の変更をすべて速く・安全にするため。

| 順 | Phase | 分類 | 内容 | 完了の目安 |
| --- | --- | --- | --- | --- |
| 1 | **13 方針の再定義・保存の差分更新**（今回） | A | 計画の見直し。書き込みの記録（ChangeTracker）と差分の反映、保存時の全件の読み込みの除去、再計算の無駄の除去 | 50,000件の保存の改善を前後で計測 → [PHASE13_RESULTS.md](PHASE13_RESULTS.md) |
| 2 | 14 大量データの仕上げ | A | ①通知の集約（期限超過が数万件のとき、1件ずつの通知ではなく「ほか N件」にまとめる。通知の過多を防ぐ UX の分析も含む）②再計算の分離（データの種類ごとに、変わったものだけを計算し直す）③起動の短縮（50,000件で約2秒。部分読み込み・書類などの遅延読み込み）④タスク一覧の並べ替えの軽量化 | 50,000件で保存・一覧・検索が1秒以内（デスクトップ相当） |
| 3 | 15 バックアップと復旧の改善 | A | エクスポート/インポートの改善：バックアップの勧め（最後のバックアップからの日数の表示）、復元前の差分の表示（何が増える・消えるか）、部分的な復元（データの種類を選ぶ）、取り込み時の検証の強化、大きなデータ（原本ファイル）の扱い。File System Access API（保存先のフォルダーへの書き出し。Chromium のみ）は B として試す | 復元の失敗・破損ファイル・旧版のファイルでのテスト |
| 4 | 16 設計品質・保守性 | A | `AppData` の分割（データの保持・派生値の計算・通知の記録を分ける）、サービスの書き込みの共通化（操作の単位の明確化）、使われていないコード・重複の整理、依存ライブラリの更新の手順。変更のしやすさを、変更に必要なファイル数などで測る | 既存のテストがすべて合格。整理の前後で行数・依存関係を比較 |
| 5 | 17 操作性の磨き込み | A | 主要な業務フローの操作回数と到達性の再計測（Phase 10 の記録と比較）。複数の製品（Todoist・Linear・Notion・kintone など）の設計の比較（メタ理解設計）から、導入する価値のあるものだけを採用 | 改善前後の操作回数 |
| 随時 | 実験 | B | 下表。ブランチで試し、計測して価値があるものだけを main に残す。残さないものは結果だけを記録する | 実験ごとに結果を記録 |

### 実験の候補（B）

| 実験 | 学ぶこと | 判断の基準 |
| --- | --- | --- |
| Web Worker で派生値（統計・通知・提案）を計算 | メインスレッドの分離・データの受け渡しの費用 | 保存・入力の応答が改善し、コードが複雑になりすぎない |
| OPFS ＋ SQLite（WebAssembly）と IndexedDB の比較 | 保存方式による性能・クエリの違い | 計測のみ。移行は、明確な利点がある場合に別途判断 |
| Service Worker によるオフライン対応（PWA） | キャッシュの戦略・更新の通知 | GitHub Pages で無料で動く範囲 |
| 仮想スクロール（一覧の表示中の部分だけを描画） | 描画の最適化・アクセシビリティとの両立 | 「さらに表示」より操作性が良い場合のみ |
| クラウド技術の学習（必要になった場合） | 認証・データベース・同期 | **本体には導入しない**。別の実験として、費用0の範囲・送信するデータを示して事前承認を得てから |
