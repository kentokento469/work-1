# Phase 12 — 性能・日付処理・拡張性

実施日：2026-10-17
環境：開発サーバー（Linux・Chromium〔Playwright 1.56〕のデスクトップ表示）。実機の iPhone・低性能な PC では**未計測**（数値は環境によって変わる。相対的な改善の比較として扱う）。

## 1. 性能の計測（12.1）

### 1.1 方法

`e2e/perf.spec.ts`（通常のテストでは実行しない。`PERF=1` のときだけ）で、タスク 1,000 / 10,000 / 50,000 件と、比例した社員（件数 / 20、最低50名）・問い合わせ（件数 / 10）を IndexedDB に直接入れて、次を計測した。デモデータ（書類・在庫・操作履歴など）も含む。

| 指標 | 内容 |
| --- | --- |
| 起動 | 再読み込みから、ダッシュボードの表示まで |
| タスク一覧 | 画面の移動から、一覧の1件目の表示まで（全件のスコープ） |
| 検索 | 検索欄に入力してから、件数の表示が変わるまで |
| 絞り込み | 「未完了」に切り替えてから、一覧の表示まで |
| 保存 | クイック追加の「追加」から、完了の通知まで（保存 → 全データの再読み込み → 再計算 → 再描画を含む） |
| 画面の移動 | ダッシュボード → 社員 → ヘルプデスクの3画面 |
| メモリ | JS ヒープの使用量（ガベージコレクション後）・DOM のノード数 |

### 1.2 結果（ミリ秒。改善前 → 改善後）

| 指標 | 1,000件 改善前 | 1,000件 改善後 | 10,000件 改善前 | 10,000件 改善後 | 50,000件 改善後 |
| --- | --- | --- | --- | --- | --- |
| 起動 | 233 | 216 | — | 401 | 1,291 |
| タスク一覧 | **3,792** | 607 | — | 672 | 954 |
| 検索 | **1,637** | 435 | — | 649 | 802 |
| 絞り込み | 317 | 103 | — | 312 | 927 |
| 保存 | **1,889** | 372 | **120秒以内に完了せず** | 741 | 2,184 |
| 画面の移動（3画面） | 466 | 382 | — | 628 | 791 |
| 描画した一覧の件数 | 1,041 | 100 | 10,000 | 100 | 100 |
| DOM ノード数 | 56,215 | 10,974 | — | 15,671 | 27,671 |
| JS ヒープ | 12MB | 8MB | — | 22MB | 76MB |

改善前の 10,000件は、計測全体に 9分以上かかり、保存の完了を 120秒待っても確認できなかった（実用できない）。50,000件の改善前は計測していない（10,000件で実用できないため）。

### 1.3 原因と改善（12.2）

| 原因 | 影響 | 改善 |
| --- | --- | --- |
| **一覧の各行が全タスクを探していた**（親タスク・サブタスク・前提タスク・問い合わせ・資産・プロジェクトを `find`/`filter`）。件数 × 件数の計算量 | 1,000件で約300万回、10,000件で約3億回の比較を、表示・入力・保存のたびに実行 | データの読み込み時に1回だけ索引（ID → データ、親 → サブタスク）を作り、各行は索引から引く（`domain/dataIndex.ts`） |
| **一覧を全件描画していた** | 1,000件で DOM が約5.6万ノード。検索の1文字ごと・保存のたびに全件を描き直す | 一覧を100件ずつ表示し「さらに表示（残り N件）」「すべて表示」（`ui/ShowMore.tsx`）。タスク・社員・問い合わせ・書類の一覧、ボードの各列（50件ずつ）。絞り込み・検索を変えると先頭から。通知などから特定の項目へ移動した場合は、その項目まで表示する |
| タスクの絞り込みの「対象社員」の候補を、社員 × タスクで計算 | 社員が多いと遅い | 索引（タスクの対象になっている社員）で判定 |
| 見出しの「未完了・期限超過」の件数を描画のたびに全件で計算 | 不要な再計算 | 1回の計算でまとめて数え、データが変わったときだけ計算 |

### 1.4 性能の基準と限界

| 基準（デスクトップ相当の端末） | 10,000件 | 50,000件 |
| --- | --- | --- |
| 起動 2秒以内 | ○ 0.4秒 | ○ 1.3秒 |
| 一覧・検索・絞り込み・画面の移動 1秒以内 | ○ 0.3〜0.7秒 | ○ 0.8〜0.95秒 |
| 保存 1秒以内 | ○ 0.7秒 | **× 2.2秒** |

- **推奨の上限：タスク 10,000件程度**（主要な操作がすべて1秒以内）。50,000件でも動作するが、保存のたびに約2秒待つ
- 50,000件の保存が遅い原因：保存のたびに**全データを IndexedDB から読み直し、ダッシュボードの統計・通知・自動化の提案をすべて再計算**する設計（Phase 1 からの全件読み込み方式）。差分の更新（変わったデータだけを読み直す）は、データの読み込み・通知・自動化の判定をすべて作り替える必要があり、変更の範囲が大きいため今回は行わない。複数利用者・サーバーの導入（Phase 13〜15）で、データの取得を部分読み込み（ページング・サーバー側の検索）に変える際にあわせて設計する
- iPhone などの性能の低い端末では、上の数値より遅くなる（**実機では未計測**）
- 全件読み込み方式のため、メモリはデータ量に比例する（50,000件で JS ヒープ 76MB）。書類の元ファイル（画像・PDF）は一覧の読み込みに含めない（Phase 4 から）

## 2. 日付処理の共通化（12.3）

### 2.1 営業日（`domain/calendar.ts`）

| 機能 | 内容 |
| --- | --- |
| 日本の祝日 | 祝日法の規則から端末内で計算（外部への通信なし）。振替休日・国民の休日を含む。2020・2021年の東京オリンピックの特例、2019年の即位に伴う休日も対応。2025・2026年の祝日を内閣府の公表と照合 |
| 会社の休業日 | 設定画面「営業日・休業日」で、休みの曜日（既定：土日）・祝日を休みにするか・会社の休業日（日付・年末年始の一括追加）を設定。祝日の出勤日（`workdays`）もデータとして保持 |
| 営業日の計算 | 営業日の判定・休みの理由、前の営業日・次の営業日、n 営業日後、営業日数 |
| 適用先 | 入社準備タスクの期限（前倒し）、問い合わせの対応期限（受付から n 営業日）、自動化で作るタスクの期限、問い合わせからのタスクの期限。**これまでは土日だけを避け、祝日に期限が入っていた** |

制約：春分・秋分の日は天文計算の近似式による推定（官報の発表は前年2月）。将来の法改正も反映されない。設定画面で説明し、会社の休業日で補正できるようにした。

### 2.2 繰り返しタスク（Phase 7 の残課題）

| 機能 | 内容 |
| --- | --- |
| 休みの日の扱い | 次回の期限が休みの日なら「前の営業日」「次の営業日」「そのまま（既定）」。調整前の予定日を記録し、次回はそこから計算する（例：毎週月曜で祝日を火曜にずらしても、翌週は月曜に戻る。毎月10日を8日に前倒ししても、翌月は10日） |
| 完了日基準 | 「完了した日から」（例：完了から1か月後）。Phase 7 では期限基準のみだった |

### 2.3 タイムゾーン・日付と日時

- 日付（期限など）は端末の現地の日付（`YYYY-MM-DD`）、日時（作成・更新）は ISO 形式の UTC。日付の計算は現地時刻の日付で行い、`toISOString`（UTC）を日付に使わない（Phase 1 からの方針を確認）
- 単体テストを **日本・米国太平洋（夏時間あり）・ニュージーランド・UTC** の4つのタイムゾーンで実行し、すべて合格（日数の差・月末・うるう年・繰り返し・営業日）

## 3. 共通インターフェースの整理（12.4）

- 営業日の計算を `domain/calendar.ts` に集約し、自動化・入社準備・問い合わせ・タスク提案の各所にあった「土日なら前倒し」の個別の処理を置き換えた
- データの索引（`domain/dataIndex.ts`）と一覧の段階表示（`ui/ShowMore.tsx`）を共通部品にした
- 過剰な抽象化は避けた（データアクセスの抽象化は Phase 13 の設計で扱う）
