# Phase 10 — 業務フロー中心の UX・アクセシビリティ

実施日：2026-10-17
環境：Node.js 22 / Chromium（Playwright 1.56）/ axe-core 4.14（@axe-core/playwright 4.14）。「iPhone」は Chromium の iPhone 13 エミュレーション。WebKit は CI の参考ジョブ（GitHub Actions）。**実機の iPhone Safari・スクリーンリーダー（VoiceOver・NVDA）では未検証**。

## 1. 業務フローの通し監査（10.1・10.2）

デモデータを使い、E2E の操作手順と画面のソースから、各業務を最後まで終える最小の操作（タップ・入力・選択）を数えた。下表の「改善後」は今回の修正後に E2E で実測した値（`e2e/phase10.spec.ts`）。

| 業務 | 改善前の操作数・画面遷移 | 見つかった問題 | 改善 | 改善後 |
| --- | --- | --- | --- | --- |
| 入社（登録 → 準備タスク → 機器の手配） | 12操作・3遷移 | タスク登録後の画面に、次の作業（必要な機器の予約・発注の提案）への導線がない。自動化センターへ移動し、提案を探して開く必要があった | 登録結果に「必要な機器の提案を確認」。対象の提案を強調表示して開く | 機器の手配までの移動が「移動＋探す＋開く」から1タップに（E2E で 3操作以内を確認） |
| 退職（退職日 → 返却確認タスク → 資産の返却） | 資産1台あたり 13操作・4遷移 | 資産の「返却」と返却確認タスクの「完了」を別の画面で二重に記録していた（返却後に社員の画面へ戻ってタスクを完了にする往復） | 返却の画面に「返却確認タスクも完了にする（データの消去・初期化を確認済み）」（初期値で選択）。1回の操作で両方を記録 | 資産1台あたり 11操作・3遷移（返却の画面での操作は2タップ） |
| 退職予定者の画面 | — | 退職予定（退職日あり）の社員にも「入社準備タスクを自動生成」が表示されていた | 退職日のある社員には表示しない | — |
| 問い合わせ（受付 → タスク → 解決 → 完了 → FAQ） | 20操作・3遷移 | 解決内容の欄に入力した文（未保存）が「解決済みにする」のダイアログに引き継がれず、入力し直しが必要だった | 入力中の解決内容をダイアログに引き継ぐ | 再入力 0回（E2E で確認） |
| 在庫不足 → 発注 → 承認 → 入荷 | 6操作・2遷移 | **申請者の名前が承認者の欄に残り、そのまま承認できた**（申請者と承認者が同じ入力欄。本人による承認を防げない） | 状態が変わったら名前の欄を空にする。**申請者本人の承認を拒否**（空白の違いも同一人物とみなす）。ログインがないため氏名の一致による判定 | 操作数は同じ。誤った承認を防止（E2E・単体で確認） |
| 書類（取り込み → 確認 → 確認完了） | 約8操作・2遷移 | 確認完了の後は通知だけで、次の書類の取り込み・一覧への導線がない | 確認完了の直後に「次の書類を取り込む」「書類一覧へ」 | 連続して取り込む場合の移動 1タップ |
| 一般タスク・プロジェクト | タスク2件で 12操作 | 作成したプロジェクトが開かず、一覧から探して開き直す必要があった | 作成するとそのまま開く（すぐにクイック追加でタスクを入れられる） | タスク2件で 11操作（E2E で 1件追加までの 5操作を確認） |
| 自動化の承認 | 2〜3操作・1遷移 | 処理履歴に作成されたタスク・対象への導線がない。「見送る」は元に戻せない | （未対応 §6） | — |

改善前後の数値は、同じデモデータ・同じ手順（最短経路）で数えた操作数。所要時間（秒）は、操作の速さが人によって大きく異なるため計測していない（自動テストの実行時間は実際の操作時間を表さない）。

### 監査で見つかったが今回は変更しなかった点（理由）

| 点 | 理由 |
| --- | --- |
| 社員の登録後の「入社準備タスクを生成しますか？」の確認 | 既存社員の登録（入社準備が不要な場合）もあるため、移動するかを選べる確認として残す |
| 書類の取り込み後に解析が自動で始まらない | OCR のデータ（数MB）の取得を伴う場合があるため、利用者の操作で開始する設計を維持 |
| 発注候補から複数の発注書ができた場合に一覧に留まる | 仕入先ごとに発注書が分かれるため、どれを開くかを利用者が選ぶ現状を維持（一覧に新しい下書きが表示される） |
| 自動化の処理履歴から結果への移動・見送りの取り消し | 処理履歴に作成した対象の ID を残すデータ構造の変更が必要。Phase 11（監査ログの整理）で操作履歴とあわせて設計する |

## 2. 利用者像と主な業務（10.3）

アクセス制御（権限）としては扱わない（Phase 13〜14 で設計）。現在の画面がどの利用者のどの業務を支えているかを整理し、各業務の「次の作業」が同じ画面から開けることを優先して改善した。

| 利用者 | 主な業務 | 主に使う画面 | 今回の改善 |
| --- | --- | --- | --- |
| 一般社員 | 問い合わせの起票、自分のタスク | ヘルプデスク（受付）、タスク | キーボードだけでの操作、表示のコントラスト |
| 総務・人事 | 入社・退職、書類の確認、備品 | 社員、入社準備、書類、在庫 | 入社準備 → 機器の手配、返却とタスクの同時記録、書類の連続取り込み |
| 情報システム | 問い合わせ対応、IT資産、アカウント | ヘルプデスク、在庫（IT資産）、自動化センター | 解決内容の引き継ぎ、返却時のデータ消去確認 |
| 管理職 | 承認、進捗の確認 | 発注書、ダッシュボード、プロジェクト | 本人承認の防止、プロジェクトの作成から作業開始まで |
| 経営者 | 全体の把握 | ダッシュボード、通知センター | 部署別の内訳の読み上げ（名前と表示の一致） |

利用者ごとに表示を切り替える（ダッシュボードの並び替えなど）は、利用者とロールの概念（Phase 13）がないと「誰の表示か」を決められないため、Phase 13 の設計で扱う。

## 3. アクセシビリティ（WCAG 2.2 AA）監査（10.4）

### 3.1 自動検査（axe-core・WCAG 2.0/2.1/2.2 の A・AA）

対象：全28画面＋主要なダイアログ5種（社員の登録・タスクの作成〔詳細を開いた状態〕・社員の削除の確認・デモデータの初期化の確認・入力エラーの表示）× ライト／ダーク × デスクトップ／iPhone 相当。`e2e/a11y.spec.ts` として CI に組み込み、**違反があれば公開しない**。

| 問題（axe のルール） | 件数（修正前・ライト/ダーク各） | 原因 | 修正 |
| --- | --- | --- | --- |
| 文字のコントラスト不足（1.4.3） | 全画面 | 補足の文字に使う標準の slate-400（白で 2.6:1）・slate-500（slate-100 で 4.3:1、ダークの紺で 3.1:1） | テーマの色をモードごとに調整（ライト：白で 5.4〜6.5:1、ダーク：紺で 5.8〜6.8:1）。選択中のタブの件数表示（ダーク）・ダークでの入力エラーの文字も修正 |
| 進捗バーに名前がない（4.1.2） | 3画面 | `role="progressbar"` に名前がない | 「入社準備の進捗」「プロジェクトの完了率」などの名前と、読み上げ用の値（%） |

## 4. Safari（WebKit）で画面の移動が失われる不具合（Phase 8・9 の WebKit の失敗の原因）

CI の WebKit ジョブで、失敗時の画面の状態（アクセシビリティツリー）と URL の移り変わりをログに出すようにし、原因を特定した。

| 事象 | 原因 | 修正 |
| --- | --- | --- |
| 社員を登録して「タスクをプレビュー」を押すと、入社準備の画面に移った直後に社員一覧へ戻る（W2・毎回発生） | ダイアログを閉じたときの「履歴を1つ戻す」処理と画面移動の競合。Chromium は移動の直後に履歴の状態が更新されるが、WebKit はしばらく古い状態のまま見えるため、戻る処理が実行されて移動を取り消していた | 画面移動（置き換え）の最中は戻る処理を行わない。閉じた直後の移動では予約済みの戻る処理を取り消す。URL を変える他の処理（作成したプロジェクトを開くなど）は、戻る処理が終わってから実行する共通の仕組み（`afterModalHistory`） |
| 起動直後に別の画面へ移動すると、URL は変わっているのに画面が切り替わらない（在庫・データ管理など・不定期） | 画面の切り替えを、最初の描画の後に URL の変化の監視を始めていた。WebKit では描画後の処理が遅れることがあり、その間の移動を取りこぼしていた | 監視の開始時に、最初に描画した画面と現在の URL を比べて追いつく |

これらは実機の Safari でも起きうる（特に動作の遅い端末）。実機での確認は**未検証**。修正後の WebKit ジョブの結果は §5。
