# Phase 3 開発計画（案）— Phase 2 時点の計画

> **この文書は Phase 2 終了時点の計画です。** Phase 3 では在庫・備品・購買管理（下記「優先度：中」の在庫・発注管理を拡張したもの）を実装しました。結果は [PHASE3_RESULTS.md](PHASE3_RESULTS.md)、残りの項目と次の計画は [PHASE4_PLAN.md](PHASE4_PLAN.md) を参照してください。

Phase 2 で「問い合わせ → 分類 → 解決策 → タスク → 完了 → 分析」の流れが動くようになった。
Phase 3 では、この共通基盤（タスク・履歴・分類ルール・取り消し・冪等処理）を再利用して残りのモジュールを追加し、
デモ環境から実運用へ近づけるための土台を整える。

## 1. 優先度：高（業務改善効果が大きいもの）

| 項目 | 内容 | 再利用する Phase 1・2 の仕組み |
| --- | --- | --- |
| 請求書・領収書処理（モジュール3） | 受領 → 内容入力 → 勘定科目の候補提示 → 承認 → 支払タスク。重複受領（同じ請求番号・金額・取引先）の検出 | 分類エンジン（キーワード→勘定科目）、冪等キー、タスク連携、秘密情報検出（口座番号の扱い） |
| 退職手続きの自動化 | 退職日からアカウント停止・PC回収・社会保険手続きタスクを自動生成 | 入社準備エンジン（ルール・期限計算・重複防止）をそのまま流用 |
| 申請者のセルフサービス窓口 | 社員が自分で問い合わせを登録し、入力中に FAQ を見て自己解決できる画面 | 問い合わせフォーム・FAQ候補・下書き保存 |
| 祝日カレンダー | 期限計算・SLA を祝日に対応 | `addBusinessDays` の休日判定を差し替え |

## 2. 優先度：中

| 項目 | 内容 |
| --- | --- |
| 在庫・発注管理（モジュール4） | 備品・PCの在庫数、発注点を下回ったら発注タスクを提案。ヘルプデスクの「PC在庫の確認」タスクと連動 |
| 承認フロー（モジュール5の第一歩） | 自動化エンジンの「計画（プレビュー）」を承認待ちとして保存し、承認者が確定する。現在の「プレビュー→登録」を「プレビュー→申請→承認→登録」に拡張 |
| 一括操作 | 問い合わせ・タスクの複数選択による担当者変更・ステータス変更（取り消し可能にする） |
| 分類ルールの改善支援 | 担当者がカテゴリを変更した事例を一覧化し、追加すべきキーワードを提案（採用率の分析を活用） |
| CSV インポート | 社員・FAQ の一括取り込み（検証・プレビュー付き） |
| PWA 化 | オフライン表示・ホーム画面アイコン |

## 3. 実運用に向けた基盤（デモ環境からの移行）

| 項目 | 内容 |
| --- | --- |
| バックエンドと認証 | 複数端末・複数ユーザーでデータを共有するため、サーバーとログインを導入。現在のサービス層を API の背後へ移す（ドメイン層は純粋関数なので移植可能） |
| 権限管理 | 管理者・担当者・一般社員の役割。カテゴリ・ルールの編集は管理者のみ |
| 監査ログ | 操作履歴に操作者を記録、改ざん防止 |
| 差分更新 | 変更のたびの全データ再読込をやめ、変更分だけ反映（データ量増加に備える） |

## 4. 品質・検証
- **実機 iPhone Safari での検証**（Phase 2 では未実施）を最初に行う
- 利用者を想定したユーザビリティテスト（実演ガイドの各ステップの所要時間を計測）
- 大量データ（問い合わせ 5,000件程度）での一覧・検索・集計の性能測定
- 自動分類の評価用データセットを作り、カテゴリ別の正解率を測定（現在は採用率のみ）

## 5. 作業順（案）
1. 実機検証と Phase 2 の不具合修正
2. 退職手続きの自動化（既存エンジンの流用で短期間）
3. 請求書・領収書処理
4. 承認フロー（請求書処理で必要になるため）
5. 在庫・発注管理
6. バックエンド・認証の設計（移行計画の作成）
