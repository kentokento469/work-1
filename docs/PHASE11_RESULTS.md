# Phase 11 — セキュリティ・監査ログ・個人情報保護

実施日：2026-10-17
環境：Node.js 22 / Chromium（Playwright 1.56）。WebKit は CI の参考ジョブ。外部の診断ツール・第三者による診断は使っていない（**第三者のセキュリティ診断は未実施**。Phase 16 で別途必要）。

## 1. OWASP を参考にした監査（11.1）

現在の構成は「静的ファイル（GitHub Pages）＋ブラウザ内の保存（IndexedDB・localStorage）」で、サーバー・ログイン・外部 API はない。OWASP Top 10（2021）と、クライアント側で起こりうる問題の観点で、ソースコードを確認した。

| 観点 | 確認した内容 | 結果 | 対応 |
| --- | --- | --- | --- |
| XSS（A03） | `dangerouslySetInnerHTML`・`innerHTML`・`eval`・`new Function`・`document.write` の使用 | 使用なし（React のエスケープに依存） | — |
| **危険なファイルの扱い（A03・A04）** | 書類の取り込みは拡張子だけでも画像と判定し、ブラウザが報告した種類（MIME）をそのまま保存。「原本を拡大表示」は blob: URL（**アプリと同じオリジン**）を新しいタブで開く | **問題あり（P1）**：拡張子だけ `.png` にした SVG（スクリプト入り）を取り込む、または細工したバックアップを復元すると、原本を開いたときにアプリと同じオリジンでスクリプトが動きうる（端末内のデータの読み取り・改ざん） | 保存・表示・ダウンロードのすべてで、種類を JPEG・PNG・WebP・GIF・BMP・HEIC・PDF に限定し、それ以外は `application/octet-stream`（表示せずダウンロード）として扱う（`domain/documents/safeMime.ts`）。バックアップの復元時も置き換える。既に保存済みの書類にも表示時に適用される |
| インラインスクリプト・外部スクリプト（A05） | CSP なし。`index.html` にインラインのスクリプト | 問題あり（P2）：XSS が起きた場合の被害を抑える仕組みがない | **CSP を導入**（本番ビルドの meta）。インラインのスクリプトを禁止し、テーマの初期化を別ファイルへ |
| **意図しない外部通信**（A05・A10） | `fetch` の使用先：郵便番号データ・OCR のデータ（いずれも WorkCore 自身から配信） | 外部への通信はない。ただし将来の変更・依存ライブラリによる外部送信を防ぐ仕組みはなかった | CSP の `connect-src 'self'`・`default-src 'self'` で、**外部への通信・外部の画像/スクリプトの読み込みをブラウザが遮断**。E2E で「通常の操作で外部に通信しない」「外部への送信・注入したスクリプトは遮断される」を検証 |
| 入力の検証（A03・A08） | 画面の入力は各サービスで検証済み（Phase 1〜）。バックアップの取り込みは形式・参照・ハッシュを検証（Phase 8・9） | 関連データの種類（`links.kind`）・処理履歴の対象は任意の文字列を受け入れていた | 既知の種類だけを受け入れる |
| CSV インジェクション | CSV の各セルの先頭の `= + - @` | 既に対策済み（先頭に `'`） | — |
| URL・画面移動 | `#/...?focus=` の値を CSS セレクターに使う箇所 | `CSS.escape` 済み。リンクの組み立ては `encodeURIComponent` | — |
| 不正な URL への移動（A01） | `javascript:` などの URL を開く箇所 | 外部 URL へ移動する機能はない。リンクはすべて `#/` から始まるアプリ内の画面 | — |
| 依存ライブラリの脆弱性（A06） | `npm audit` | 0件。CI で high 以上があれば公開しない（Phase 8） | — |
| 機密情報・シークレット（A02・A07） | リポジトリ内の API キー・トークン・パスワード | なし（外部サービスを使っていない） | — |
| 機密情報の入力 | 問い合わせ・下書きにパスワード等が入力される可能性 | 既存の検出（Phase 2）：保存前に警告・伏せ字、下書きには保存しない | — |
| エラーによる情報の露出（A04・A09） | 想定外のエラーで、例外のメッセージ（`Cannot read properties of undefined` など）を利用者に表示 | 問題あり（P3） | 利用者向けの説明と開発者向けの記録を分離（§4） |

### クライアントだけでは防げない問題（サーバー導入後に対策が必要）

| 問題 | 理由 | 対策の時期 |
| --- | --- | --- |
| 端末を使える人は誰でも全データを閲覧・変更・削除できる | ログイン・権限がない。データは端末内にある | Phase 14（認証・権限） |
| 操作履歴は改ざん・削除できる（監査ログにならない） | 端末内の記録は、その端末の利用者が書き換えられる。ハッシュの連鎖などを端末内で作っても、作り直せるため意味がない | Phase 14〜15（サーバー側の追記専用の記録） |
| 端末内のデータ（IndexedDB）は暗号化されていない | 鍵を端末内に置くと保護にならず、毎回のパスワード入力が必要になる | Phase 13 で認証とあわせて設計 |
| クリックジャッキング（`frame-ancestors`） | GitHub Pages は応答ヘッダーを設定できず、meta の CSP では指定できない | ホスティングの変更時（Phase 14〜） |
| 発注の承認者などの本人確認 | 氏名の入力による判定（Phase 10）で、なりすましは防げない | Phase 14 |

## 2. 操作履歴と監査ログの役割（11.2）

| | 操作履歴（現在） | 監査ログ（将来） |
| --- | --- | --- |
| 目的 | 利用者が「最近何をしたか」を確認する・誤操作に気付く | 誰がいつ何をしたかを、後から証明できる形で残す |
| 保存先 | 端末内（IndexedDB）。最大300件で古いものから消える | サーバー（追記のみ・削除不可） |
| 改ざん耐性 | **なし**（画面にも明記） | 必要（サーバー側で管理） |
| 操作した人 | 記録しない（利用者の概念がない） | ログインした利用者 |
| 時期 | 現在 | Phase 14〜15（外部基盤の導入にはオーナーの承認が必要） |

今回の対応：データ管理の操作履歴に「この端末内の記録で、改ざん・削除を防ぐ監査ログではありません」と表示。操作履歴の種類の絞り込みに「自動化」を追加。

### Phase 10 からの引き継ぎ（自動化の処理履歴）

- 処理履歴に、作成・変更した対象（タスク・資産・品目・社員・問い合わせ）を記録し、履歴から直接開けるようにした（削除済みの対象は「（削除済み）」と表示）。それ以前の記録には対象がないため表示しない
- 「見送る」の直後に「元に戻す」を表示（見送りの記録を消すと、同じ提案がまた表示される）

## 3. 個人情報の扱い（11.3）

| データ | 個人情報 | 目的 | 保存期間・削除 | 外部への送信 |
| --- | --- | --- | --- | --- |
| 社員 | 氏名・社員番号・所属・役職・雇用区分・入社日・退職日・連絡先（メール・電話・住所）・備考 | 入社・退職の準備、機器の貸与、問い合わせの申請者 | 削除するまで。**退職者の連絡先・備考は「個人情報の整理」で削除できる**（今回追加）。社員の削除で完了済みタスクには氏名・社員番号だけを残す（Phase 9） | なし |
| 問い合わせ | 申請者の氏名（受付時点）・件名・内容・コメント・解決内容 | 対応の記録・FAQ 化 | 削除するまで | なし |
| 書類 | 請求書・領収書などの内容（発行元・金額・氏名・住所が含まれうる）と原本 | 経費・購買の記録 | ゴミ箱 → 完全削除で原本も削除 | なし（OCR も端末内） |
| タスク・資産・操作履歴 | 担当者名・利用者名（自由入力・氏名） | 業務の記録 | 操作履歴は最大300件 | なし |
| 入力途中の下書き（localStorage） | 入力中の内容 | 途中離脱からの復帰 | 送信・破棄で削除。パスワード等を含む場合は保存しない | なし |
| 上書き前の退避（Phase 9） | 全データの1世代 | 誤操作からの復旧 | 次の上書きで置き換え | なし |
| バックアップファイル | 全データ | 端末の故障・移行への備え | 利用者が管理（**暗号化を推奨**：Phase 9） | 利用者が持ち出す場合のみ |

外部への送信がないことは、CSP（`connect-src 'self'`）でブラウザが強制し、E2E で検証している。

**未対応**：保存期間の自動適用（例：退職から N 年で自動削除）は、会社ごとの規程で期間が異なるため、設定の設計（Phase 13）とあわせて扱う。現在は利用者の操作で削除する。

## 4. エラーの分類と表示（11.4）

| 分類 | 例 | 利用者への表示 | 開発者向け（コンソール） |
| --- | --- | --- | --- |
| 入力（input） | 必須項目・重複・業務ルール（本人承認など） | 原因と直し方（項目の横にも表示） | 記録しない |
| 整合性（conflict） | 別のタブの変更との競合・参照先の削除 | 何が起きたかと、選べる操作（Phase 9） | 記録 |
| 保存（storage） | 容量不足・接続切れ・中断 | 「変更は取り消され、元のデータは残っている」＋対処（Phase 9） | 記録 |
| 権限（permission）・通信（network） | 将来（ログイン・サーバー導入後） | — | 記録 |
| システム（system） | プログラムの誤りなど想定外 | 一般的な説明だけ（**技術的なメッセージを表示しない**：今回修正） | 記録（例外の詳細） |

起動時のエラー（Phase 8）は、利用者向けの説明と「開発者向けの情報」（折りたたみ）を分けて表示済み。

## 6. 残存リスク・次への引き継ぎ

- 第三者のセキュリティ診断・ペネトレーションテストは未実施（Phase 16）
