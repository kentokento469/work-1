## 2. 設計上の判断

| 判断 | 理由 |
| --- | --- |
| 社員の削除では、**未完了**のタスク（とそのサブタスク）だけを削除し、**完了済み**のタスクは関連付けを外して削除時点の氏名・社員番号（`formerEmployee`）を残す | 未完了のタスクは「その社員のための準備・作業」で、社員がいなくなれば不要。完了済みのタスクは業務の記録で、誰の作業だったかが後から分かる必要がある。退職者は従来どおり削除ではなく「退職」を推奨 |
| 編集の競合は、フォームを開いた時点の更新日時との比較で検出（楽観的ロック）し、保存を止めて「最新を読み込む／上書き」を選ばせる | 最終保存優先で黙って上書きしない（計画書の方針）。ロック（編集中は他のタブで編集不可）はタブの閉じ忘れで解除されない問題があるため採用しない |
| 別のタブへは「変わった」ことだけを `BroadcastChannel` で通知し、受け取ったタブが自分で読み直す | データ本体を送らない（同じ端末・同じブラウザ内だけで完結）。入力中のフォームは ID で初期化しているので消えない |
| 上書き前の退避は**別のデータベースに1世代だけ**。退避できなければ上書きしない | 本体の移行・置き換えの影響を受けない。複数世代は容量を圧迫する。取り消せない上書きをしないことを優先 |
| 「直前のデータに戻す」は、戻す前の状態も退避する | 誤って戻した場合も、もう一度押せば戻せる |
| 暗号化は Web Crypto の PBKDF2（SHA-256・600,000回）＋ AES-GCM（256ビット）。鍵・パスワードは保存しない | ブラウザ標準で外部サービス・追加ライブラリが不要。AES-GCM は改ざん・破損も検出する。反復回数は OWASP の PBKDF2-SHA256 の推奨値 |
| 暗号化は任意（既定は無効） | パスワードを忘れると誰にも復元できないため、利用者が意味を理解して選ぶ。持ち出す場合に推奨と表示 |
| 移行後の点検は最初の起動で1回だけ。参照切れは修復し、直せない問題は通知 | 毎回の起動で全件を点検すると遅くなる。移行の直後が最も問題が起きやすい |

### 暗号化の制約（利用者向けの説明に記載）

- パスワードを忘れると、そのバックアップは誰にも（開発者にも）復元できない。パスワードの再設定・回復の手段はない
- 暗号化されるのはファイルの中身だけ。ファイル名・作成日時・ファイルの大きさは隠れない
- 端末内のデータ（IndexedDB）は暗号化していない（端末のロック・OS の保護に依存）。端末内データの暗号化は、鍵をどこに置くか（毎回のパスワード入力が必要になる）という運用上の問題があり、Phase 13 の設計で認証と合わせて検討する
- 誤ったパスワードと、ファイルの改ざん・破損は区別できない（どちらも「復号できません」）

## 6. 残存リスク・制約

- **端末の故障・紛失・ブラウザのデータ削除**：データは端末内だけにあり、上書き前の退避も同じ端末内のため一緒に失われる。完全な対策はサーバー側の正本とバックアップ（Phase 15 以降・外部サービスの導入にはオーナーの承認が必要）。現状は JSON バックアップを別の場所に保存する運用で補う
- 競合の検出はタスク・社員の編集フォームのみ。問い合わせ・品目・書類などは、別のタブの変更の自動反映はあるが、同時に編集した場合は後から保存した方が優先される（在庫数・発注などはトランザクション内で現在の値から計算するため数値の不整合は起きない）
- `BroadcastChannel` が無い古いブラウザでは別のタブの変更は自動で反映されない（再読み込みで反映。競合の検出は動く）
- 退避は1世代だけ。退避の後にもう一度上書きすると、最初の状態には戻せない
- 自動削除からの保護（`persist()`）を許可するかはブラウザが決める。iPhone Safari での挙動は**未検証**（実機が必要）
- 暗号化バックアップの作成・復号は、600,000回の鍵の導出のため端末によって数秒かかる可能性がある（作成中はボタンに読み込み中を表示）。所要時間は計測しておらず、実機では**未検証**
- 端末内のデータ自体は暗号化していない（§2）
- WebKit（CI の参考ジョブ）：Phase 8 の2回目の実行では2件の失敗（郵便番号からの住所補完・入社準備のプレビュー）。Phase 10 の iPhone 検証で扱う（`PHASE8_RESULTS.md` §4.1）
