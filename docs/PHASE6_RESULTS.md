## 2. 設計：共通通知システム

| 層 | 実装 |
| --- | --- |
| 通知の導出（`src/domain/notifications.ts`） | `deriveNotices()` が実データ（タスク・問い合わせ・在庫・発注書・書類・自動化提案・社員・処理履歴）から毎回導出する純粋関数。保存した件数・ダミー通知は使わない |
| 通知の項目 | ID（`種類:対象ID`、同じ原因から1件だけ）、種類（`type`）、区分（`kind`：期限超過／承認待ち／未処理／注意／お知らせ）、発生元機能、対象（種類＋ID）、タイトル、発生理由、必要な操作、発生日時、優先度、遷移先（ディープリンク）、未処理に数えるか |
| 未読・履歴 | 設定ストア（IndexedDB v5、Phase 5 で追加済み）に `notifications` として「初回検出・解消・既読」を記録（`syncNoticeLog`・`markNoticesRead`）。DB のバージョンは上げていない（既存データは変わらない） |
| バッジ | すべて `navNoticeSummary()` で数える。数字 = **未処理**（対応が終わるまで残る）。色は最も重い区分（期限超過がある時だけ赤、承認待ちは紫、未処理は紺、注意は黄） |
| 画面 | 通知センター（`#/notifications`）、各画面上部の「要対応」（`AttentionSection`）、詳細画面の「なぜ表示されているか」（`TargetNotices`）、ダッシュボードの「対応が必要なこと」、メニューの「対応が必要な項目」と項目ごとの件数 |
| 対象へのフォーカス | 遷移先 URL の `focus=<対象ID>` と、要素の `data-focus-id`。`useFocusHighlight()`（`src/app/focus.ts`）が描画を待って対象までスクロールし、控えめに強調表示（2.4秒・減らす設定ではアニメーションなし）。終わったら `focus` を URL から外す（戻る操作で再強調しない）。絞り込みで隠れていれば解除して表示、見つからなければ「すでに対応済み・削除された可能性」を案内 |

### 通知の種類（現在の対象）

| 通知 | 区分 | 発生条件 | 消える条件 | 遷移先 |
| --- | --- | --- | --- | --- |
| タスクの期限超過 | 期限超過 | 未完了で期限 < 今日 | 完了・期限変更・削除 | タスク画面の「要対応」で対象を強調（その場でステータス変更可） |
| 問い合わせの期限超過 | 期限超過 | 未解決で期限 < 今日 | 解決・完了・期限変更 | 問い合わせ詳細（理由と操作を上部に表示） |
| 新しい問い合わせ | 未処理 | ステータス「新規」（期限超過のものは上の1件だけ＝二重に数えない） | 受け付け | 問い合わせ詳細 |
| 在庫不足 | 注意 | 利用可能数 < 最低在庫数 | 入庫・発注残で解消 | 品目詳細 |
| 発注書の承認待ち | 承認待ち | 承認申請中 | 承認・差し戻し・取り消し | 発注書詳細 |
| 書類の確認待ち | 未処理 | 確認待ち（ゴミ箱を除く） | 確認完了・削除 | 書類詳細 |
| 自動化の承認待ち | 承認待ち | 有効なルールの承認待ち提案 | 承認・見送り・状況の変化 | 自動化センターで対象の提案を開いた状態で強調 |
| 入社準備の未完了 | 注意 | 入社まで7日以内で未完了の準備タスクがある | 準備タスクの完了 | 入社準備画面（対象社員を選択した状態） |
| 自動実行のお知らせ | お知らせ（件数に含めない） | 直近7日に自動実行された処理 | 既読（一覧の未読から外れる）・7日経過 | 自動化センターの処理履歴で強調 |

### 未読と未処理の区別

- **未処理**：業務が終わるまで残る。読んだだけでは減らない。ナビの数字・「要対応」・通知センターの「未処理」はすべてこの件数で一致する
- **未読**：通知を開いた（通知から移動した、詳細画面で表示した）か。ヘッダーのベルの数字。通知センターで「すべて既読にする」ができる
- **解消済み**：原因がなくなった通知の履歴（直近30日・最大300件）。同じ原因が再発すると未読・未処理に戻る

## 4. 検証中に発見・修正した不具合

| 不具合 | 原因 | 修正 |
| --- | --- | --- |
| 問い合わせのバッジが、新規かつ期限超過の問い合わせを2回数える | 2つの件数を足していた | 通知は1対象1件（期限超過を優先） |
| 社員登録のダイアログに入力中、背景でデータが再読み込みされると入力が消える（自動実行の完了時などに発生。Phase 5 の E2E が iPhone で検出） | 初期値の再計算が「社員一覧」の変化に反応していた | ダイアログを開いた時だけ初期化。タスク・品目・資産・問い合わせの編集ダイアログも、対象のオブジェクトではなく ID で判定するよう同じ修正 |
| 一覧の絞り込みを変更した直後に URL の変更が届くと、画面の絞り込みが古い値に戻ることがある | 絞り込みの URL 書き換えを state の更新処理の中で行っていた | URL を先に書き換えてから state を更新（共通フック `useQueryState`） |
| 対象を指定して移動したとき、前回のスクロール位置の復元と対象へのスクロールが競合する | 復元は画面単位で行っていた | `focus` 付きの遷移では位置を復元しない |

## 6. 残っている制約

- 下部ナビのバッジ自体は個別のボタンにしていない（タブの中の小さな数字を別ボタンにすると誤タップが増えるため）。代わりに、タブを押した先の画面上部に必ず「要対応」を表示し、ヘッダーのベル（44×44px）から通知センターへ移動できる
- 通知はこの端末のブラウザ内のデータから作る。複数端末・複数ユーザー間での既読の共有、プッシュ通知（アプリを閉じている間の通知）はない（サーバーを導入しない方針）
- 「期限間近（3日以内）」はダッシュボードの「優先対応」に表示するが、通知（未処理件数）には含めない（期限前の作業を「未処理」として赤や件数で示すと過剰になるため）
- 実機 iPhone Safari での表示・スクロール・強調表示のアニメーション・戻る操作は未検証（Phase 5 から継続）
- 画面の切り替えでは画面単位で描画し直す（先読みによりちらつきは抑えているが、タブごとの状態をメモリに保持する方式にはしていない）。一覧の条件は URL に、スクロール位置は画面ごとに保持している
