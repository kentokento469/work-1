# UX 監査 — Phase 1 機能と Phase 2〜4 追加時の確認

> Phase 3 の監査は §5、Phase 4 は §6 を参照。

実施日：2026-10-15
方法：(1) Playwright で iPhone 13 相当の画面を実際に操作して計測、(2) 画面のスクリーンショット確認、(3) コードレビュー
重要度：**高** = データ消失・誤操作につながる／**中** = 操作効率・理解を妨げる／**低** = 軽微

## 1. 実測で確認した問題と対応

| # | 重要度 | 観点 | 現象（Phase 1） | 確認方法・実測値 | 対応 | 検証 |
| --- | --- | --- | --- | --- | --- | --- |
| A1 | 高 | 入力内容の消失 | 社員登録など入力中のモーダルで背景をタップすると、確認なしに閉じて入力が消える | 実測：氏名入力→背景タップ→モーダルが閉じ、再度開くと氏名は空 | 未保存の変更がある時だけ「入力した内容は保存されていません／編集を続ける・破棄して閉じる」を表示。変更がなければ即閉じる（過剰な確認を避ける） | E2E「途中離脱・誤操作からの復帰」 |
| A2 | 高 | 元に戻せない操作 | タスク削除は「取り消せません」の確認ダイアログのみ | 実測：ダイアログ文言「この操作は取り消せません」 | 確認ダイアログを廃止し、即削除＋通知の「元に戻す」。ステータス変更・ルール削除にも適用。社員削除は確認を残しつつ取り消しも可能に | E2E（削除→元に戻す→件数が戻る） |
| A3 | 中 | 一覧に戻ると消える検索条件 | 社員一覧で検索・部署を指定→詳細→戻ると条件が空 | 実測：戻った後の検索語 `""`、部署 `""` | 条件を URL に保存（`replaceState` で履歴を増やさない）。社員・タスク・問い合わせ・FAQ の各一覧に適用 | E2E（詳細→戻る後に検索語保持） |
| A4 | 中 | 小さすぎるタッチ領域 | タスク一覧のステータス選択の高さ 36px | 実測：36px | スマホで 44px に拡大（PCは 36px のまま） | コード確認・E2E（下部ナビ ≥44px） |
| A5 | 中 | 操作後の表示・誤操作 | 成功通知がスマホ画面の上端に出てヘッダーを覆う。片手操作では「閉じる」に指が届きにくい | 実測：通知の top = 20px | スマホでは下部ナビの上（親指の届く位置）に表示、PCは右上。取り消しボタン付きの通知は表示時間を長く（8秒） | スクリーンショット |
| A6 | 中 | スマホで見づらい一覧 | （Phase 2 で絞り込み項目が増えた結果）問い合わせ・タスク一覧で、検索欄＋絞り込み4〜5個が画面を占め、一覧が画面外に押し出される | スクリーンショット（iPhone 13 幅）で一覧の先頭が見えない | スマホでは詳細フィルターを「絞り込み」に折りたたみ、設定中の条件数をバッジ表示。PCは常時展開 | スクリーンショット・E2E |
| A7 | 中 | 不要な画面遷移／状態の喪失 | 詳細から一覧に戻るとスクロール位置が先頭に戻る | コードレビュー（画面遷移時に常に `scrollTo(0)`） | 画面ごとにスクロール位置を記録し、戻ったときに復元。タブ切替などクエリだけの変更ではスクロールしない | 実測（iPhone 13 相当）：タスク・問い合わせ・社員の各一覧で 1200px → 詳細 0px → 戻る 1200px。E2E にも追加 |
| A8 | 中 | 不必要な読み込み | 全画面のコードを初回に読み込む（Phase 2 追加で JS が gzip 129KB に増加） | ビルド結果 | 使用頻度の低い画面・ヘルプデスクを遅延読み込みし、初回表示後に先読み（遷移時の読み込み待ち＝ちらつきを防ぐ）。初回 JS gzip 129KB → 102KB | ビルド結果 |
| A9 | 低 | ナビゲーションの拡張性 | 下部ナビが5項目で埋まり、ヘルプデスクを追加できない | 構造上の問題 | 頻度の高い4項目（ホーム・問い合わせ・タスク・社員）＋「メニュー」に再構成。入社準備・FAQ・データ・設定はメニューから。PCのサイドバーは全項目 | E2E（Phase 1 のナビテストをメニュー経由に更新して合格） |
| A10 | 低 | 複雑すぎる設定画面 | 部署マスタが「入社準備 → 準備ルール設定」の中にあり、ヘルプデスクからも使う設定なのに見つけにくい | コードレビュー | 「設定」画面を新設し、問い合わせカテゴリ・部署マスタ・表示テーマを集約 | スクリーンショット・E2E（設定画面の表示・横スクロールなし） |
| A11 | 低 | 表示テーマの不整合 | テーマ状態をコンポーネントごとに持つため、設定画面とヘッダーで表示がずれる可能性（Phase 2 で設定画面を追加して顕在化） | コードレビュー | テーマをモジュール単位の共有ストア（`useSyncExternalStore`）に変更 | E2E（テーマ切替） |

## 2. Phase 2 の新機能で最初から対策した項目

| 観点 | 対策 |
| --- | --- |
| 重複入力 | 申請者は社員マスタから選択し、部署は自動表示。担当者・期限はカテゴリから自動入力。問い合わせ→タスクは内容を引き継ぐため再入力不要 |
| 入力内容の消失（途中離脱） | 問い合わせ登録は下書きを自動保存し、再訪時に「前回の入力途中の内容を復元しました」と表示（破棄も可能） |
| 連打・二重送信 | 冪等キー（requestId）＋送信中のボタン無効化 |
| わかりにくいエラー | 完了できない理由をチェックリストで表示（解決済みか・解決内容・タスク完了・申請者確認）。秘密情報は「何が」含まれるかを表示し、ワンタップで伏せ字化 |
| 操作後に何が起きたかわからない | 登録直後に「◯◯として受け付けました」と次の操作を表示。タスク作成で問い合わせが自動で「対応中」になる場合は通知に明記。全変更を対応履歴に記録 |
| 保存状態の不明確さ | 解決内容の未保存時は「未保存の変更があります」を表示、変更がなければ保存ボタンを無効化 |
| 誤解を招く数値 | 件数不足の指標は「データ不足（n件 / 必要m件）」。解決時間の定義を画面に明記。自動分類の「採用率」は正解率ではないと注記 |

## 3. 確認したが変更しなかった項目

| 観点 | 判断 |
| --- | --- |
| 無意味なアニメーション | 画面遷移のフェード（160ms）とモーダルのスライドは状態変化の理解を助けるため維持。`prefers-reduced-motion` で無効化される（Phase 1 から対応済み） |
| 変更のたびの全データ再読込 | デモ規模（数百件）では体感差がなく、整合性を優先して維持。データ量が増える場合は Phase 3 で差分更新を検討 |
| 社員削除の確認ダイアログ | 関連タスクも同時に消える影響の大きい操作のため確認を残した（取り消しも追加） |

## 5. Phase 3 追加時の監査

実施日：2026-10-15　方法：Playwright（iPhone 13 相当・デスクトップ）での操作・計数、スクリーンショット確認、コードレビュー

### 5.1 実測で確認した問題と対応

| # | 重要度 | 観点 | 現象 | 確認方法・実測値 | 対応 | 検証 |
| --- | --- | --- | --- | --- | --- | --- |
| B1 | 高 | 自動化の誤動作 | 故障の問い合わせで代替機を承認すると、貸し出した代替機を「故障機」として再び提案する | E2E で承認後も提案カードが1件残る（「AST-0020 の代替機なし（入荷待ち）」） | 資産を動かした問い合わせは対応済みとして判定しない | 単体2件・E2E |
| B2 | 高 | 元に戻せない操作 | 入庫・出庫・移動・在庫調整を取り消せない（誤入力すると調整で打ち消すしかなく、理由入力が必要） | コードレビュー | 通知の「元に戻す」で逆向きの記録を追加（履歴は消さない）。二重取り消し・マイナス在庫になる取り消しは拒否 | 単体・E2E |
| B3 | 中 | わかりにくいエラー | 問い合わせ登録で、自動分類でカテゴリが入った後も「カテゴリを選択してください」が残る | E2E のページスナップショット（カテゴリ選択済みなのに [invalid]） | 値が変わった項目のエラーを消す | E2E |
| B4 | 中 | スマホで一覧が見えない | 在庫画面で要約カード（2列×2段）とタブ・検索で最初の画面が埋まり、品目が見えない | スクリーンショット（iPhone 13 幅）：1件目の品目が画面下端の通知の裏 | スマホでは要約を1行4列に圧縮（タップで絞り込みは維持） | スクリーンショット比較：1件目の品目名が画面内に表示 |
| B5 | 中 | 状態の喪失 | 一覧→詳細→戻るのスクロール位置復元が、負荷の高い時に失敗する | E2E 全体実行時に1回失敗（600px → 0px） | 描画が間に合うまで最大2秒再試行 | E2E 全体を2回実行して合格 |
| B6 | 低 | ナビゲーションの拡張性 | 下部ナビに在庫を追加する枠がない | 構造上の問題 | 下部ナビを「ホーム・問い合わせ・在庫・タスク・メニュー」に変更。社員管理・自動化センターはメニューへ（PCのサイドバーは全項目）。承認待ちの提案数をメニューにバッジ表示 | E2E（Phase 1 のナビテストをメニュー経由に更新して合格） |

### 5.2 Phase 3 の新機能で最初から対策した項目

| 観点 | 対策 |
| --- | --- |
| 操作回数 | 入社者の機器準備は「提案を開く → 承認」。入荷数は未入荷数が初期値。一覧のカードから直接「入庫」「出庫」「貸出」「返却」 |
| 重複入力 | 入社者の部署・入社日から必要機器を判定、発注書は候補から品目・数量・仕入先・単価を引き継ぐ、故障時は申請者の使用中機器を自動特定 |
| 確定と提案の区別 | 発注候補は紫の「下書き」表示で「発注書を作るまで確定ではありません」と明記。発注書もアプリ内の記録で、外部発注・送信しないことを画面に表示 |
| 連打・二重処理 | 全ての数量操作・貸出・返却・入荷・発注書作成に requestId、送信中のボタン無効化 |
| 入力ミス | 数量は ± ボタン＋変更後の在庫のプレビュー。利用可能数を超える出庫はボタンが無効 |
| 片手操作 | ± ボタン 56px、シートの決定ボタンは画面下部 |
| 保存状態 | 棚卸は入力途中を端末に自動保存し、確定前に差異の件数を確認 |
| 誤解を招く数値 | 在庫額は「参考在庫額（参考単価 × 数量）」と表示し、会計上の評価額ではないと明記。資産は取得価額を別に表示 |
| 何が起きたか分からない | 自動化の結果を「処理履歴」に、在庫の変化を入出庫履歴に、資産の変化を資産履歴に記録。提案には実行条件（根拠）を表示 |

### 5.3 確認したが変更しなかった項目

| 観点 | 判断 |
| --- | --- |
| 提案カードの折りたたみ | 提案が3件以上だと折りたたむため1タップ増える（入社者の機器準備は3操作）。一覧性を優先して維持 |
| 発注候補の初期選択 | すべての候補が選択済みで表示される。1品目だけ発注する場合は他のチェックを外す必要があるが、通常は不足品目をまとめて発注するため維持 |

## 6. Phase 4 追加時の監査

実施日：2026-10-15　方法：Playwright（iPhone 13 相当・デスクトップ）での操作、スクリーンショット確認、コードレビュー

### 6.1 確認した問題と対応

| # | 重要度 | 観点 | 現象 | 確認方法 | 対応 |
| --- | --- | --- | --- | --- | --- |
| C1 | 高 | 誤操作 | OCR の準備（ダウンロード）中に「解析を開始」を押せ、OCR なしで解析されて画像PDFが読めない | E2E（画像PDFの合計が空） | 準備中は解析ボタンを無効化 |
| C2 | 高 | 誤認識の見逃し | 大きな見出しの誤読で種類・合計が取れない／発行元の誤読で重複警告が出ない | E2E | 本文の定型句・登録番号・表記の近さも使って判定（PHASE4_RESULTS §4） |
| C3 | 中 | 通知の重なり | 取り込み直後に「取り込みました」「抽出しました」の通知が2つ重なり、スマホでは操作ボタンを覆う | スクリーンショット | ファイル取り込みの通知は注意事項があるときだけにした |
| C4 | 中 | 状態の喪失 | 一覧→詳細→戻るでスクロール位置がまれに先頭に戻る（Phase 2 の画面） | E2E 反復 | 画面を離れる時点の位置も記録し、ブラウザの自動復元を無効化 |
| C5 | 低 | 入力の取りこぼし | 在庫の数量シートを開いた直後の入力が初期化で戻ることがある（Phase 3 の画面） | E2E | 描画前に初期化 |
| C7 | 中 | 情報の不足（Phase 1 のダッシュボード） | 部署別社員数が単色の棒で総数だけを示し、実働人数と人員の変動（入社予定・退職予定・休職）が分からない | オーナーの指摘 | 部署ごとに在籍中・入社予定・退職予定・休職中・退職済の積み上げバーに変更。凡例を追加し、右端は在籍人数（在籍中＋退職予定＋休職中）、内訳は文字でも常に表示（ホバー不要）。少人数の区分も最小6pxで表示。ダーク表示でも色を調整 |
| C6 | 低 | ナビゲーション | 下部ナビは5項目で埋まっているため「書類」を追加できない | 構造上の問題 | 下部ナビは変えず（既存の操作を崩さない）、メニューの先頭・ダッシュボードの書類カード（「取り込む」）・社員/問い合わせ/発注書の「関連書類」から入れるようにした。PCのサイドバーには「書類管理」を追加。確認待ちの件数をメニューのバッジに含めた |

### 6.2 最初から対策した項目

| 観点 | 対策 |
| --- | --- |
| 次の操作がわかる | 取り込み画面は4つの入口だけ。取り込み後は自動で解析パネルを表示し、終わると確認画面へ。確認画面の下部に「確認完了まで：重要項目 あと n件（…）」を常に表示 |
| 一画面に詰め込みすぎない | スマホは「原本／項目」を切り替え（PCは左右に並べる）。確認不要な項目は折りたたみ |
| 片手操作・タップ領域 | 取り込みの入口は高さ112px以上のタイル、チェックボックスの行は44px以上、操作ボタンは画面下部に固定（下部ナビ・Safe Area の上） |
| 作業を失わない | 原本は取り込んだ時点で保存、入力途中は自動保存、解析はキャンセル・手入力に切り替え可能、削除はゴミ箱経由で元に戻せる |
| 操作結果の明示 | 抽出した項目数、修正前の値、処理履歴（取り込み・抽出・一時保存・確認完了・在庫反映）、在庫反映済みの表示 |
| 視覚的一貫性 | 既存の Card・Badge・Modal・タブ（丸いチップ）・通知をそのまま使用。既存画面のデザインは変更していない |

## 7. Phase 5 追加時の監査

### 7.1 確認した問題と対応
| 問題 | 対応 |
| --- | --- |
| 詳細画面の「一覧へ戻る」が新しい履歴を積むため、ブラウザの戻るで詳細に戻ってしまい、一覧の条件が初期化されることがある | 直前の履歴が一覧なら `history.back()` で戻る（`BackLink`） |
| モーダルを開いた状態で戻る・スワイプをすると、モーダルごと前の画面に移り入力が消える | モーダルを履歴の一段として扱い、先にモーダルを閉じる。入力途中なら破棄確認 |
| ホーム画面から起動するとスワイプで戻れない | 単独起動のときだけ左端スワイプを実装 |
| 電話番号・郵便番号・住所を毎回手で整えて入力する | 自動整形・住所補完・入力候補（§README Phase 5） |
| 連絡先の電話番号を消すと連絡先欄が閉じる（Phase 5 の実装中に E2E で検出） | 欄の開閉を利用者の操作に任せる |

### 7.2 未確認事項
iPhone 実機（Safari 標準のスワイプとの共存、単独起動時のスワイプのしきい値、日本語キーボード）での確認は未実施。
