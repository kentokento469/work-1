## 2. 抽出した原理と WorkCore での実装

### P1. 失敗を「確認」で防ぐより「取り消せる」ようにする（R1 User Control and Freedom, R8, R11）
- **共通する理由**：確認ダイアログは毎回出ると読まれずに押される。取り消しがあれば、操作は速いまま誤操作から復帰できる
- **採用**：タスク削除・ステータス変更・問い合わせ削除・FAQ削除・ルール削除・社員削除を、通知の「元に戻す」で復元可能にした。タスク削除の確認ダイアログは廃止
- **成立条件の検証**：WorkCore の削除は関連データ（社員→タスク、問い合わせ→タスクの紐付け）を伴うため、単純な取り消しでは整合性が崩れ得る → サービス層で「削除時に関連データを返し、復元時に紐付け先の存在を確認して戻す」形にした（`restoreTask` は紐付け先が消えていれば紐付けを外して復元）
- **例外**：社員削除（関連タスクも消える影響の大きい操作）とデータの全削除・復元は確認を残した。影響の大きさで使い分ける
- **検証**：E2E「途中離脱・誤操作からの復帰」でタスク削除→元に戻す、単体テストで問い合わせ削除→復元（タスク紐付けの復元を含む）

### P2. 二重処理を仕組みで防ぎ、再試行を安全にする（R3）
- **理由**：決済では「通信が切れたので再送したら二重課金」を冪等キーで防いでいる。スマホの連打・電波不安定でも同じ問題が起きる
- **採用**：問い合わせフォームを開くたびに `requestId` を発行し、サービス層は同じキーなら最初の結果を返す（`meta` ストアに記録）。加えて問い合わせ番号に DB の一意インデックス
- **不採用**：Stripe の「24時間でキー失効」は採用しない。ローカル保存でデータ量が小さく、失効させる必要がないため
- **検証**：単体テスト（同じ requestId で3回同時送信→1件のみ作成）、E2E（送信ボタンをダブルクリック→1件）。開発中に採番の不具合（インデックスの `getAllKeys` が主キーを返す）を DB の一意制約が検出した

### P3. 最初は重要なものだけ見せ、詳細は求められたときに見せる（R2, R12）
- **理由**：地図はズームに応じて表示を変え、NN/g は「最初は少数の重要な選択肢だけ」を推奨。スマホの小さな画面では特に効く
- **採用**：
  - 自動分類は「候補（カテゴリ・優先度）」だけを表示し、根拠（一致語・点数表・加点理由）は「判定の根拠を見る」で展開
  - スマホの一覧は検索欄だけを常時表示し、詳細フィルターは「絞り込み（件数）」に折りたたむ。**条件が隠れていても件数バッジで気付ける**ようにした（隠れた条件で結果が減る、という段階的開示の副作用への対策）
  - 問い合わせ詳細では、状態に応じた「次にやること」を1つだけ強調
- **検証**：iPhone 幅の監査で、一覧の検索結果がフィルターに押し出されて画面外になっていた問題を確認 → 折りたたみで解消（スクリーンショットで確認）

### P4. 状態を保持し、元いた場所に戻れるようにする（R7）
- **理由**：OS は中断しても元の画面に戻れるよう状態を保存する。業務アプリで「詳細を見て戻ったら検索条件が消えた」は監査で実測された問題
- **採用**：一覧の検索条件を URL に保存（履歴を増やさない `replaceState`）、画面ごとのスクロール位置を復元、問い合わせ登録の下書きを端末に自動保存（秘密情報を含む場合は保存しない）、モーダルは未保存の変更がある場合だけ破棄確認
- **検証**：E2E で「詳細→戻る」後の検索語保持、再読み込み後の下書き復元、背景タップ時の破棄確認

### P5. 「解決した」と「閉じた」を分ける（R9）
- **理由**：ヘルプデスク製品は担当者の解決（Solved）と最終的なクローズ（Closed）を分け、依頼者が再度連絡できる余地を残している
- **採用**：解決済み（解決内容必須）と完了（申請者確認・解決内容・関連タスク全完了が必須、以後編集不可）を分離。タスク完了で問い合わせを自動では閉じない
- **不採用**：Zendesk の「解決済みから一定日数後に自動クローズ」は採用しない。申請者確認を明示的に記録することを優先した（小規模組織では担当者が直接確認できるため）
- **検証**：単体テスト（完了条件3つ、完了後の変更不可）、E2E（タスク未完了では完了ボタンが無効）

### P6. 優先度は「影響範囲」と「緊急性」を分けて評価する（R10）
- **理由**：「ログインできない」は1人の不便のこともあれば全社停止のこともある。症状の語だけで優先度を上げると過剰判定になる
- **採用**：加点グループを「セキュリティ」「影響範囲」「業務停止」「時間的緊急性」「低緊急表現」に分け、**グループごとに1回だけ加点**。高優先度は合計3点以上（例：影響範囲＋業務停止、またはセキュリティ単独）。「急ぎません」が「急ぎ」として加点されないよう最長一致を使う
- **検証**：単体テスト（「ログインできない」→中、「社内全員がネットワークに接続できない」→高、「至急 緊急 今すぐ」→1点のみ、「急ぎません」→低）

### P7. 説明を読ませず、操作しながら覚えさせる（R13：二次情報のため着想として利用）
- **採用**：ダッシュボードの「実演ガイド」は手順を1つずつ示し、**実際の操作履歴から自動でチェックが付く**（ガイド専用の状態を持たない）。各画面の空状態にも次の操作を表示
- **検証**：E2E で、業務フローを一通り操作するとガイドが 0/6 → 5/6 → 6/6 と進むことを確認

### P8. タッチ領域は十分な大きさにする（R4, R5, R6）
- **採用**：主要な操作要素を 44px 以上に統一（WCAG 2.5.8 の最低 24px を上回り、iOS の一般的な推奨値に合わせた）。監査でタスクのステータス選択が 36px だったため 44px に修正（PCでは36px）
- **検証**：E2E で iPhone 幅の下部ナビのリンク高さ ≥ 44px、全主要画面で横スクロールなし

### P9. 非破壊的な編集・プレビュー（R11）
- **採用**：自動処理（分類・タスク提案）は「候補」として提示し、担当者が確認・変更してから確定。担当者が手で変えた項目は以後自動で上書きしない。編集内容は対応履歴に差分として残す
- **検証**：E2E（優先度を手で変えた後に本文を変えても上書きされない）、単体テスト（編集差分の履歴）

### 5.2 抽出した原理と WorkCore での実装

#### P10. 状態を上書きせず、変化を記録として積み上げる（R14、会計の元帳）
- **共通する理由**：会計は残高を書き換えず仕訳を積み上げ、誤りは赤黒の訂正仕訳で直す。だから「なぜこの数になったか」を後から説明でき、改ざんにも気付ける
- **採用**：在庫数を直接書き換える API を作らず、すべて入出庫履歴（stockMovements）経由にした。取り消しも履歴を消さず、逆向きの記録を追加（P1「取り消せる」と両立）。資産も削除せず、状態変化を資産履歴（assetEvents）に残す
- **成立条件の検証**：Event Sourcing の「履歴の再生で状態を作り直せる」性質が成り立つよう、**実在庫＝入出庫履歴の合計**を不変条件とし、全単体テストの後とバックアップ復元時に検査。改ざんしたバックアップ（在庫だけ +7）は E2E で拒否されることを確認
- **不採用**：状態を履歴からのみ計算する完全なイベントソーシング。保管場所ごとの在庫を毎回再計算するより、在庫表（stockLevels）と履歴を同じトランザクションで更新する方が、ブラウザ内の小規模データでは単純で速い。代わりに一致を検査する

#### P11. 「ある」「使える」「確保済み」「入荷予定」を分けて数える（R15）
- **理由**：EC では「棚にある数」と「売ってよい数」が違う。混同すると二重販売や欠品が起きる。社内備品でも「入社予定者に確保したPC」を別の人に渡す事故が同じ構造で起きる
- **採用**：実在庫・予約・利用可能・入荷待ち需要・発注残・計画中を分け（ARCHITECTURE §9.1）、出庫・予約は利用可能数の範囲だけ。発注残は在庫に足さず、見込みにだけ加える（入荷完了前の在庫加算を防ぐ）
- **変更点**：Shopify の Incoming は「入荷途中の在庫」だが、WorkCore では「承認済み発注の未入荷数」に置き換えた（社内の購買では、承認＝発注確定の目安になるため）。下書き・承認待ちは「計画中」として別に数え、推奨数量の二重計上を防ぐ
- **検証**：単体テスト（予約分は出庫不可、発注残は onOrder に入り onHand は不変）、E2E（予約で利用可能数だけが減る）

#### P12. 発注点は「見込み」で判定し、根拠を見せる（R17：二次情報のため着想として利用）
- **理由**：発注点はリードタイム中に減る分を見越して早めに発注するための考え方。今の在庫数だけで判定すると、すでに発注済みの分を二重に発注する
- **採用**：「見込み在庫（利用可能 − 入荷待ち需要 + 発注残）＜ 最低在庫数（発注点）」で不足と判定し、推奨数量 ＝ 適正在庫 − (見込み + 計画中)。発注候補には判定の根拠（各数量）を表示
- **不採用**：日次需要 × リードタイム ＋ 安全在庫による自動計算。需要の実績データ（数か月分の出庫）が無い段階では推定値が不安定なため、最低在庫数は担当者が設定し、仕入先にリードタイムを記録するにとどめた（Phase 4 で出庫実績からの提案を検討）
- **検証**：単体テスト（承認済み発注があると候補を作らない、見送った候補は不足が続く間は再作成しない）

#### P13. すべてを1つの取引として扱い、途中で失敗したら何もなかったことにする（R16、R3 の冪等性）
- **理由**：銀行の振替は「出金だけ成功」が許されない。在庫でも「出庫は記録されたが予約は残った」は台帳を壊す
- **採用**：1つの業務操作（例：入荷 → 在庫加算 → 資産登録 → 入荷待ち予約への引き当て → 発注候補の同期 → 操作履歴）を1つの IndexedDB トランザクションで実行し、業務エラーは `abort()` で全体を取り消す。連打・再読み込みは `requestId`（P2）で防ぐ
- **検証**：単体テスト（古い提案の実行失敗時に予約が1件も残らない、同時出庫で在庫を超えない）、E2E（ダブルクリックで1回分）

#### P14. 自動化は「提案 → 承認 → 実行」に分け、実行条件と結果を残す（Phase 2 の P9 を部門横断へ拡張）
- **理由**：自動処理が黙って在庫や資産を動かすと、担当者は何が起きたか分からず信頼できない。一方で毎回すべて手作業では自動化の意味がない
- **採用**：在庫・資産を変える操作は「要承認」、取り消しやすいタスク作成や発注候補（下書き）は「自動可」に分類。提案には実行条件（根拠）・実行内容・注意を表示し、チェックで一部だけ実行できる。結果は「実行・見送り・失敗・自動」として処理履歴に残す
- **成立条件の検証**：提案と承認の間にデータが変わる可能性がある → 承認時に同じトランザクション内で判定をやり直し、前提が変わっていれば実行しない
- **検証**：単体テスト（古い提案の拒否、並び順に依存しない判定、見送った提案は再表示しない）、E2E（入社・故障・退職の各提案を承認、見送り後の再読み込み）

#### P15. スマホでは表を縮めず、カードと「その場の操作」にする（R18：二次情報、R2 の段階的開示）
- **採用**：在庫一覧は品目ごとのカード（利用可能数を大きく、実在庫・予約・入荷待ち・発注残を小さく）に、入庫・出庫ボタンを直接配置。数量入力は片手で押せる大きな ± ボタン（Stepper）と変更後の数量のプレビュー。資産一覧は行ごとに「貸出」「返却」。PC では同じカードを2列に並べる
- **検証**：E2E で在庫関連13画面に横スクロールなし。スクリーンショットで、要約カードが一覧を画面外に押し出していたことを確認し、スマホでは1行4列に圧縮

### 5.3 Phase 3 で再利用した Phase 2 の原理

| 原理 | Phase 3 での適用 |
| --- | --- |
| P1 取り消し | 入出庫は通知の「元に戻す」で逆向きの記録を追加。予約解除も元に戻せる |
| P2 冪等性 | 入出庫・貸出・返却・入荷・発注書作成・棚卸に `requestId`、自動化は処理履歴の key |
| P3 段階的開示 | 提案カードは件数が多いと折りたたみ、発注候補の「判定の根拠」は展開式 |
| P4 状態保持 | 在庫画面のタブ・検索・絞り込みを URL に保存、棚卸の入力途中を下書き保存 |
| P8 タッチ領域 | 数量の ± ボタンは 56px、主要ボタン 44px 以上 |

### 5.4 検討したが採用しなかったもの

| 案 | 出典・発想 | 不採用の理由 |
| --- | --- | --- |
| バーコード・QR読み取り | 物流・小売 | カメラ権限と実機での検証が必要。実機未検証の状態で提供しない（Phase 4 候補） |
| 発注の自動送信（メール・EDI） | EC・調達システム | 要件で外部発注・メール送信を禁止。発注書はアプリ内の記録と印刷のみ |
| 承認なしの自動予約 | — | 入社取り消し・部署変更が多い時期に在庫を勝手に拘束するため。予約は承認制にした |
| 移動平均・総平均による在庫評価 | 会計 | 会計上の評価は税務・会計方針に依存する。参考単価 × 数量の「参考在庫額」と、資産の取得価額を分けて表示し、会計評価ではないと明記 |
| 安全在庫の自動計算 | 物流 | 需要実績が少なく推定が不安定（P12） |
