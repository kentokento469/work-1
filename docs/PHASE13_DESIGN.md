## 1. 現状の構成と、複数ユーザー化で変わること

### 1.1 現状

```
ブラウザ（GitHub Pages から配信される静的ファイル）
 ├─ 画面（React）── AppData：全データを1つのスナップショットとして保持
 │                    └ 保存のたびに IndexedDB から全件を読み直し → 索引・統計・通知・自動化の提案を再計算
 ├─ サービス（業務ロジック）：WorkCoreService / TaskService / HelpdeskService / InventoryService / DocumentService
 │     └ IndexedDB のトランザクションを直接使う（57か所）。検証・業務ルール・操作履歴の記録を同じトランザクション内で行う
 └─ IndexedDB（25 ストア）・localStorage（下書き・表示設定）
```

すでに複数利用者に備えた性質があるもの：

| 性質 | 内容 | 複数利用者での使い道 |
| --- | --- | --- |
| ID は端末で作る UUID | `generateId()`（`crypto.randomUUID`） | オフラインで作成したデータの ID をサーバーで振り直さなくてよい |
| 二重処理の防止 | 在庫・資産・入荷の操作は `requestId` を記録し、同じ操作の再送を無視する（Phase 3） | 送信待ちの再送の重複防止にそのまま使える |
| 同時編集の検出 | `expectedUpdatedAt` で、編集開始後に他のタブで変更されていたら保存を止める（Phase 9） | サーバーでの版の確認（§5.4）に置き換える |
| 複数タブの反映 | BroadcastChannel で他のタブに変更を通知（Phase 9） | サーバーからの変更通知と同じ入口にする |
| 書き込みのまとまり | 1つの操作の書き込みは1つのトランザクション（`guardTx`）。途中で失敗したら何も残らない | 同じ単位をサーバー側のトランザクションにする |
| 業務ルールの検証 | `domain/validation.ts` など、画面から独立した純粋な関数 | 画面での即時の検証にはそのまま使い、サーバーでも同じルールで再検証する |

### 1.2 複数ユーザー化で変わること

| 観点 | 現在 | 複数ユーザー化後 |
| --- | --- | --- |
| データの正本 | 端末の IndexedDB | **サーバーのデータベース**。端末のデータは表示用のコピー（キャッシュ）と送信待ち |
| 利用者 | なし（端末を使える人が全権限） | ログインした利用者。組織・役割・部署で操作を制限（§3） |
| 権限の判定 | なし | **サーバー側で判定**（RLS・サーバーの処理）。画面の非表示は補助 |
| 同時編集 | 同じ端末の別のタブだけ | 複数の人・端末。版の確認で検出し、上書きしない（§5） |
| 在庫・発注・承認 | 端末のトランザクション | サーバー側のトランザクション（§5.5） |
| 操作履歴 | 端末内・改ざんできる・最大300件 | サーバー側の追記専用の監査ログ（誰が・いつ・何を） |
| 自動化 | 開いている端末で判定・実行 | 実行はサーバー側の一意制約で1回だけ（複数の端末が同時に実行しても重複しない） |
| 書類の原本 | IndexedDB（documentFiles） | サーバーのファイル保存（組織ごとに分離・署名付き URL で取得） |

## 2. データアクセスの抽象化

### 2.1 方針

業務ロジック（検証・業務ルール）を作り直さずに、保存先を「端末」と「サーバー」で切り替えられるようにする。**層を増やしすぎない**（Phase 12 の方針）。分けるのは次の6つ。

| 責務 | 現在の場所 | 分けた後 |
| --- | --- | --- |
| 業務ロジック（検証・状態遷移・計算） | 各サービスと `domain/` | `domain/`（純粋な関数。端末・サーバーの両方で同じ判定） |
| 書き込み（操作の実行） | 各サービスの IndexedDB トランザクション | **操作（コマンド）**として表す。実行は `CommandExecutor` が担う：端末版（今の IndexedDB の処理）／サーバー版（サーバーの処理を呼ぶ） |
| 読み込み | `loadSnapshot()`（全件） | `DataSource`：初回の取得と**変更分の取得**（全件の読み直しをやめる） |
| 認証情報 | なし | `AuthContext`：現在の利用者・組織・役割（`Actor`） |
| 同期の状態 | なし | `SyncStore`：送信待ち（outbox）・最後に取得した位置・失敗した操作 |
| 通知の生成 | `domain/notifications.ts`（スナップショットから計算） | そのまま（端末で計算）。既読の状態だけ利用者ごとにサーバーへ |

### 2.2 インターフェース（Phase 14〜15 で実装する型の案）

```ts
/** 操作（コマンド）。画面のボタン1回 = 1つの操作 = サーバーでは1つのトランザクション */
interface Command<T extends string = string, P = unknown> {
  type: T;                 // 例: 'stock.issue' / 'task.update' / 'purchase.approve'
  payload: P;
  requestId: string;       // 重複防止のキー（UUID）。再送しても同じ値
  baseVersion?: number;    // 編集の場合、編集を始めたときの版（§5.4）
  issuedAt: string;        // 端末の時刻（参考。順序の判定には使わない）
}

type CommandResult<R> =
  | { ok: true; value: R; changes: ChangeSet }               // 成功。変わったデータを返す
  | { ok: false; kind: 'input' | 'conflict' | 'permission' | 'not_found'; error: AppErrorShape }  // 再送しても成功しない
  | { ok: false; kind: 'network' | 'unavailable'; retryAfterMs?: number };                         // 再送する

interface CommandExecutor {
  execute<R>(cmd: Command): Promise<CommandResult<R>>;
}

/** 変わったデータ（追加・更新・削除）。画面のスナップショットに差分として反映する */
interface ChangeSet {
  cursor: string;                                   // 変更の通し番号（サーバーが付ける）
  upserts: Partial<Record<DataStoreName, unknown[]>>;
  deletes: Partial<Record<DataStoreName, string[]>>;
}

interface DataSource {
  loadInitial(actor: Actor): Promise<{ snapshot: DataSnapshot; cursor: string }>;
  changesSince(cursor: string): Promise<ChangeSet>;
  subscribe(onChange: (c: ChangeSet) => void): () => void;  // サーバーからの変更通知（他のタブ・他の人）
}

interface SyncStore {
  enqueue(cmd: Command): Promise<void>;
  pending(): Promise<OutboxEntry[]>;
  mark(requestId: string, state: OutboxState, detail?: string): Promise<void>;
  cursor(): Promise<string | null>;
  setCursor(c: string): Promise<void>;
}
```

### 2.3 段階的な移行（外部サービスなしで先に進められる部分）

| 段階 | 内容 | 外部サービス | 効果 |
| --- | --- | --- | --- |
| A | 今のサービスのメソッドを `Command` 経由で呼ぶ形にする（端末版の `CommandExecutor` は今の処理をそのまま呼ぶ） | 不要 | 画面とサービスの間が1つの入口になる |
| B | 保存後の全件の読み直しをやめ、操作が返す `ChangeSet` をスナップショットに反映（索引も差分で更新） | 不要 | **Phase 12 の残課題（50,000件の保存 2.2秒）の解消**。他のタブには BroadcastChannel で `ChangeSet` を送る |
| C | テスト用の「端末内の偽サーバー」（メモリ上。サーバー版と同じ契約）を作り、送信待ち・再送・競合・権限の自動テストを先に作る | 不要 | Phase 15 の同期の大部分を、承認前でも外部に送らずに検証できる |
| D | サーバー版の `CommandExecutor` / `DataSource` を実装（§6 の推奨案） | **必要（承認後）** | 複数利用者 |

A〜C は承認がなくても進められるが、Phase 13 の範囲（設計のみ）を超えるため、**承認の回答（§11）とあわせて着手の可否を確認する**。

## 3. 組織・利用者・役割のモデル

### 3.1 データのモデル

```
Organization（組織 = 契約している会社）
 ├─ Membership（所属）── User（ログインする人。認証サービスのアカウント）
 │     role: owner / admin / manager / member / viewer
 │     departmentId: 所属部署（任意）
 │     employeeId: 社員の記録との対応（任意）
 │     status: invited / active / suspended
 ├─ Invitation（招待）：メールアドレス・役割・有効期限・招待した人
 ├─ Department（部署）
 ├─ Employee（社員 = 人事の記録。ログインしない人も含む）
 └─ 業務データ（タスク・問い合わせ・在庫・資産・発注・書類・設定 …）すべてに organizationId
```

**社員（Employee）とログイン利用者（User）を区別する**理由：

| | 社員（Employee） | 利用者（User / Membership） |
| --- | --- | --- |
| 意味 | 会社に在籍する人の人事の記録 | WorkCore にログインして操作する人 |
| 例 | 入社予定者・現場の社員・パート（WorkCore を使わない人を含む） | 総務・情シス・部署の責任者 |
| 作る人 | 管理者・部署の責任者 | 管理者が招待 |
| 退職 | ステータスを「退職」（記録は残す） | 所属を「停止」にして**直ちにログイン・操作を止める**（Phase 14 の完了基準） |
| 対応 | `Membership.employeeId` で任意に対応付ける（入社準備の対象者が後で利用者になる場合など） | |

- 1人の利用者が複数の組織に所属できる（例：税理士事務所・グループ会社）。**データの取得は常に「今選んでいる組織」1つだけ**
- 退職した社員に対応する利用者は、社員の退職の登録時に「この人の利用を停止しますか」と確認する（自動では止めない。社員の記録の誤操作でログインを止めないため）

### 3.2 既存のデータの項目の変更

| データ | 追加 | 既存の項目の扱い |
| --- | --- | --- |
| すべての業務データ | `organizationId`・`version`（整数・更新ごとに +1）・`createdBy`・`updatedBy`（利用者 id） | `createdAt`・`updatedAt` は残す（表示用） |
| タスク | `assigneeUserId`（担当の利用者。任意） | `assignee`（氏名の自由入力）は残す。ログインしない人も担当にできるため |
| 発注書 | `requestedByUserId`・`approvedByUserId` | `requestedBy`・`approvedBy`（氏名）は表示用に残す。**承認の本人判定は利用者 id で行う**（今は氏名の一致） |
| 問い合わせ | `requesterUserId`（任意） | 受付時点の氏名は残す（履歴） |
| 操作履歴 | サーバー側の監査ログ（`actorUserId`・操作・対象・前後の値の要約・時刻・端末の情報）を別に作る | 端末内の操作履歴は「最近の操作」の表示用として残す |
| 自動化の処理履歴 | `(organizationId, automationId, key)` に一意制約 | 重複実行の防止をサーバーで強制 |
| 設定 | 組織の設定（営業日・自動化・個人情報の保存期間）と、利用者の設定（表示・テーマ）に分ける | 今はすべて端末の設定 |

### 3.3 役割と権限（RBAC）

役割は所属ごとに1つ。**範囲**：全体（組織のすべて）／部署（自分の部署）／本人（自分が作成・担当・申請・本人のデータ）。この表は `src/domain/permissions.ts` の `PERMISSION_MATRIX` と同じ内容で、単体テストで次を検証している：上位の役割は下位より狭くならない・停止中の所属は何もできない・申請者本人は承認できない・最後の所有者は外せない。

| 操作 | 所有者 | 管理者 | 部署の責任者 | 一般 | 閲覧のみ |
| --- | --- | --- | --- | --- | --- |
| 社員の閲覧（氏名・所属・役職） | 全体 | 全体 | 全体 | 全体 | 全体 |
| 社員の登録・変更 | 全体 | 全体 | 部署 | — | — |
| 社員の削除 | 全体 | 全体 | — | — | — |
| 社員の連絡先・備考の閲覧（個人情報） | 全体 | 全体 | 部署 | 本人 | 本人 |
| 個人情報の整理（消去） | 全体 | 全体 | — | — | — |
| 入社準備のタスクの作成 | 全体 | 全体 | 部署 | — | — |
| タスクの閲覧 | 全体 | 全体 | 全体 | 全体 | 全体 |
| タスクの作成・変更 | 全体 | 全体 | 全体 | 本人 | — |
| タスクの削除 | 全体 | 全体 | 部署 | 本人 | — |
| 問い合わせの登録 | 全体 | 全体 | 全体 | 全体 | 全体 |
| 問い合わせの閲覧 | 全体 | 全体 | 部署 | 本人 | 本人 |
| 問い合わせの対応（状態・回答・FAQ 化） | 全体 | 全体 | 部署 | — | — |
| 在庫の閲覧 | 全体 | 全体 | 全体 | 全体 | 全体 |
| 入庫・出庫・移動 | 全体 | 全体 | 全体 | 全体 | — |
| 棚卸しの反映 | 全体 | 全体 | 全体 | — | — |
| 資産の登録・貸与・返却 | 全体 | 全体 | 全体 | — | — |
| 発注の閲覧・下書き・承認申請・入荷 | 全体 | 全体 | 全体 | 全体 | — |
| 発注の承認・差し戻し（**申請者本人は不可**） | 全体 | 全体 | 部署 | — | — |
| 書類の閲覧 | 全体 | 全体 | 全体 | 本人 | — |
| 書類の登録・確認 | 全体 | 全体 | 全体 | 全体 | — |
| 書類の削除 | 全体 | 全体 | 全体 | 本人 | — |
| 自動化の提案の実行 | 全体 | 全体 | 全体 | — | — |
| 自動化の設定 | 全体 | 全体 | — | — | — |
| 組織の設定（営業日・保存期間など） | 全体 | 全体 | — | — | — |
| 利用者の招待・役割の変更・停止（所有者の付与・変更は所有者だけ） | 全体 | 全体 | — | — | — |
| データの書き出し（CSV・バックアップ） | 全体 | 全体 | — | — | — |
| データの取り込み・復元（組織のデータの置き換え） | 全体 | — | — | — | — |
| 監査ログの閲覧 | 全体 | 全体 | — | — | — |

権限の判定の場所：

1. **データベース（RLS）**：すべての表で「`organizationId` が、ログインした利用者の有効な所属の組織と一致する」行だけを読み書きできる（**組織間の分離はここで強制**）。範囲（部署・本人）の読み取りの制限もここで行う
2. **サーバーの処理（データベースの関数）**：書き込みはすべて `Command` に対応するサーバーの関数で行い、関数の先頭で権限と業務ルールを確認する。表への直接の書き込みは許可しない
3. **画面**：できない操作のボタンは表示しないか、理由を表示する（補助。1・2 が無くても守られる状態にはしない）

役割を増やす要望（例：「購買の担当」「ヘルプデスクの担当」）には、役割を増やすのではなく**所属に「担当の業務」（追加の権限）を付ける**方式で対応する（Phase 14 で必要なら）。

## 4. 正本と同期の方針

| データ | 正本 | オフラインでの扱い |
| --- | --- | --- |
| 業務データ全般 | サーバー | 最後に取得した内容を表示（「最終の同期：○分前」を表示） |
| タスク・問い合わせ・コメント・チェックリストの作成と変更 | サーバー | **送信待ちに入れて、再接続時に送る**（画面には「未送信」と表示） |
| 在庫の数量が変わる操作（入庫・出庫・移動・棚卸し・入荷・予約の引き当て）・発注の状態の変更（申請・承認・差し戻し・取消）・資産の貸与と返却・社員の削除・データの取り込み | サーバー | **オンラインのときだけ実行できる**。オフラインではボタンを押せず、理由を表示。端末の古い在庫数で判断した操作が、後でサーバーで拒否されると、現場で「出庫したはずの物」が台帳に残らないため |
| 入力途中の下書き | 端末（localStorage） | 今のまま。サーバーには送らない |
| 表示の設定（テーマ・並び順・表示件数） | 端末 | 今のまま |
| 通知の既読 | サーバー（利用者ごと） | 端末で既読にし、送信待ちで送る |
| 書類の原本 | サーバー（ファイル保存） | 取り込みはオンラインのときだけ（OCR は端末で実行し、結果と原本を一緒に送る） |

## 5. オフライン・同期・競合

### 5.1 送信待ち（outbox）

端末の IndexedDB に `outbox` ストアを追加する（DB の版を上げる。既存のデータは変えない）。

```
OutboxEntry {
  requestId, command, state, attempts, nextAttemptAt, lastError, createdAt,
  entityKeys: ['tasks:abc', ...]   // 同じデータへの操作の順序を守るため
}
state: pending → sending → done（削除） / retry（一時的な失敗） / rejected（再送しても成功しない）
```

| 項目 | ルール |
| --- | --- |
| 順序 | 同じデータ（`entityKeys` が重なる操作）は作成順に1つずつ送る。関係のない操作は並べて送ってよい |
| 再送 | 通信の失敗・サーバーの一時的な停止（`network` / `unavailable`）だけ。待ち時間は 1, 2, 4 … 最大 5分（ばらつきを入れる）。再接続・画面の再表示で直ちに再開 |
| 重複の防止 | `requestId` を毎回同じ値で送る。サーバーは組織ごとに処理済みの `requestId` と結果を**30日間**保存し、同じ `requestId` には処理せずに前回の結果を返す（今の在庫の `requestId` の仕組みをサーバーに移したもの） |
| 部分的な失敗 | 1つの操作は1つのトランザクションなので、操作の途中までの反映は起きない。複数の操作のうち一部だけが失敗した場合は、失敗した操作だけを「送信できなかった操作」に残す |
| 送信できなかった操作 | `rejected`（入力の誤り・権限・競合・対象の削除）。**黙って捨てない**。画面に一覧を表示し、内容の確認・修正して再送・破棄を選べる。破棄は利用者の操作だけ |
| ログアウト | 送信待ちがある場合は件数を表示して確認する。ログアウト時に端末のデータ（キャッシュ・送信待ち）を消す。共有の端末を考慮し、既定は「消す」 |
| 別の利用者のログイン | 端末のデータは利用者と組織ごとに分ける（データベース名に組織 id と利用者 id を含める）。他の人の送信待ちを送らない |

### 5.2 画面での表示（同期の状態）

| 状態 | 表示 |
| --- | --- |
| 同期済み | 表示しない（通常の状態） |
| 未送信あり | 見出しに「未送信 N件」。オフラインなら「オフライン（再接続すると送信します）」 |
| 送信できなかった操作あり | 警告の色で「送信できなかった操作 N件」→ 一覧へ |
| 最後の同期から時間が経っている | 「最終の同期：○時間前」（オフラインで古い情報を見ていることを示す） |

### 5.3 変更の受け取り

- サーバーの変更通知（推奨案ではデータベースの変更の購読）を受けたら、`changesSince(cursor)` で差分を取得してスナップショットに反映する（全件の読み直しはしない）
- 通知を取りこぼしても、再接続・画面の再表示・5分ごとに `changesSince` で追いつく（通知だけに頼らない）
- 自分の送信待ちがあるデータに他の人の変更が届いた場合は、画面に「他の人が変更しました」を表示し、送信時に §5.4 の競合の判定に任せる

### 5.4 競合の解決ルール（**最終更新優先で上書きしない**）

すべての行に `version`（整数）を持たせる。編集の操作は、編集を始めたときの版（`baseVersion`）と、**変更した項目だけ**を送る。

| 状況 | サーバーの動作 | 画面 |
| --- | --- | --- |
| `baseVersion` = 現在の版 | 反映し、版を +1 | — |
| 版が違う | **反映しない**。`conflict` と現在の内容を返す | Phase 9 の競合の表示（`ConflictNotice`）を拡張：「○○さんが △時に変更しました」・自分の変更と相手の変更を項目ごとに並べる・「相手の内容を確認して、自分の変更をもう一度適用」「自分の変更を破棄」 |
| 対象が削除済み | 反映しない（`not_found`） | 「他の人が削除しました」。必要なら新しく作り直す |
| 追加だけの操作（コメント・問い合わせのやり取り・チェックリストの項目の追加） | 版を確認せずに追加（他の人の追加と衝突しない） | — |
| 状態だけの切り替え（タスクの完了・チェックリストの項目の完了） | 「完了にする」「未完了に戻す」という**操作の意図**で送り、現在の状態から判定する（既に完了なら何もしない＝成功） | — |

項目ごとの自動の統合（相手と自分が別の項目を変えた場合に両方を残す）は、**初版では行わない**（判定の誤りで業務データが混ざる危険があるため）。競合の発生頻度を Phase 15 の検証で確認してから判断する。

### 5.5 サーバー側のトランザクションにする操作

次の操作は、**サーバーの関数の中で、検証から書き込み・監査ログまでを1つのトランザクションで行う**。端末は結果を受け取って表示するだけで、端末の在庫数などから結果を計算しない。

| 操作 | 守ること | 方法 |
| --- | --- | --- |
| 出庫・移動・予約の引き当て | 在庫がマイナスにならない（2人が同時に最後の1個を出庫しても、片方だけが成功） | 在庫の行をロック（`SELECT … FOR UPDATE`）してから数量を確認し、台帳（入出庫の記録）と在庫数を同時に更新 |
| 入庫・入荷 | 発注の未入荷数量を超えない。個体管理品の資産の自動登録と在庫・予約の引き当てを同時に | 発注書の行をロック |
| 棚卸しの反映 | 棚卸しの開始後に動いた数量を上書きしない | 棚卸しの開始時点の数量と比べ、差がある品目は確認を求める（Phase 3 のルールをサーバーで） |
| 入出庫の取り消し | 取り消しの重複・取り消し後の在庫のマイナスを防ぐ | 元の記録をロック |
| 発注の状態の変更 | 状態の遷移の順序（下書き → 承認待ち → 承認 → 入荷）。**申請者本人は承認できない**（利用者 id で判定）。承認の権限 | 発注書の行をロックし、現在の状態から遷移を判定 |
| 資産の貸与・返却 | 同じ資産を2人に同時に貸与しない | 資産の行をロック |
| 自動化の実行 | 同じ提案を2回実行しない | `(組織, 自動化, キー)` の一意制約 |
| 番号の採番（発注番号・書類番号・社員番号の重複確認） | 番号の重複 | 組織ごとの一意制約と採番用の行 |
| 社員の削除・個人情報の消去 | 関連するタスク・資産・予約・書類を同時に処理（Phase 9 の方針） | 1つの関数 |

業務ルールを端末（`domain/`）とサーバー（SQL の関数）の2か所に書くことになるため、**同じ入力と期待結果の表（テストケース）を共有し、両方で実行する**（Phase 15）。

### 6.2 推奨案：A. Supabase（東京リージョン）＋ 画面は GitHub Pages のまま

推奨する理由：

1. **業務データに合う**：在庫・発注・承認は「同時に操作しても数量と状態が正しい」ことが最重要（§5.5）。PostgreSQL のトランザクション・行ロック・一意制約・外部キーで、端末の処理をほぼそのまま移せる
2. **組織間の分離をデータベースで強制できる**：RLS で、サーバーの処理に誤りがあっても他社のデータを返さない（Phase 14 の完了基準「組織 A が組織 B のデータを取得・変更できないことをサーバー側の自動テストで検証」に直接対応）
3. **ロックインが小さい**：標準の PostgreSQL なので、費用・規約・事業の継続に問題が出たら、C（Cloud SQL）や国内のデータベースサービス・自社運用に移せる
4. **費用が小さく予測しやすい**：1社なら月 $25 から（§7）
5. **1つのサービスで足りる**：データベース・認証・ファイル保存・変更の通知

推奨案の弱点と対策：

| 弱点 | 対策 |
| --- | --- |
| オフライン対応を自前で作る | §5 の設計。段階 C（§2.3）で外部に送らずに先にテストを作る |
| 運営会社が米国企業 | データは東京に保存。契約（データ処理の契約・サポートによるデータへのアクセスの条件）を確認（§8・要確認） |
| 英語のサポートだけ | 障害時の手順書を日本語で整備（Phase 16）。管理画面の操作は文書化 |
| 有料プランでも、第三者の認証の報告書は上位プラン（Team, $599/月〜） | 取引先から報告書を求められるまでは Pro。求められたら Team か C/D を再検討 |
| 画面を GitHub Pages に置いたままでは、応答ヘッダー（`frame-ancestors` など。Phase 11 の残課題）を設定できない | 初版は GitHub Pages のまま（費用 0）。クリックジャッキング対策が必要になった時点で、ヘッダーを設定できる静的ホスティングへ移す（費用・事業者は要確認。移す前に別途承認） |

## 9. データ移行計画（端末のデータ → サーバー）

**前提：実在の利用者データの移行は、オーナーの明示的な許可がある場合だけ行う。デモデータは移行しない（既定で除外）。**

### 9.1 手順

| 手順 | 内容 | 失敗した場合 |
| --- | --- | --- |
| 1. 移行前のバックアップ | 端末で**暗号化したバックアップ**（Phase 9）を必ず作り、保存されたことを確認してから次へ | 次へ進めない |
| 2. 内容の確認 | データの種類ごとの件数・デモデータの有無・点検（Phase 9 の `checkIntegrity`）の結果を表示。点検で誤りがあれば修復（`repairIntegrity`）を先に | 修復できない誤りがあれば止める |
| 3. 移行先の組織 | 新しい組織を作るか、既存の組織（所有者だけ）。**既存の組織にデータがある場合は、統合ではなく「空の組織にだけ移行できる」を初版の制限にする**（重複・参照の誤りを避ける） | — |
| 4. 対応付け | 担当者・申請者・承認者（氏名の文字列）を利用者に対応付けるかを選ぶ（任意。対応付けなくても氏名は残る）。社員と利用者の対応も任意 | — |
| 5. 取り込み | サーバーの**仮の領域（取り込み用の表）**へ、データの種類ごとにまとめて送る。まとまりごとに `requestId` を付け、中断しても続きから再開できる。書類の原本はファイル保存へ送り、ハッシュ（SHA-256。Phase 9 のバックアップと同じ）で照合 | 中断：再開すると送っていない分から続ける。誤り：仮の領域を消して最初から |
| 6. 検証 | サーバーで、件数（種類ごと）・参照（タスク → 社員・部署・親タスク、資産 → 社員、発注 → 品目・仕入先 など）・一意（社員番号・品目のコード・発注番号・書類番号）・在庫の数量（台帳の合計と在庫数の一致）・原本のハッシュを検証 | 1件でも合わなければ切り替えない。結果を表示 |
| 7. 切り替え | 検証が通ったら、1つのトランザクションで仮の領域から本番の表へ移す | 失敗したら何も変わらない |
| 8. 端末の切り替え | 端末は「サーバーのデータを表示する」状態に。**端末の元のデータは消さずに30日間、読み取り専用で残す**（問題があれば元に戻す） | 30日の間は、移行前の状態に戻せる |
| 9. 操作履歴 | 端末の操作履歴は「移行前の端末内の記録（監査ログではない）」として取り込む | — |

### 9.2 移行のテスト（Phase 15）

- 旧版の DB（v1〜v6）から作ったデータ・10,000件のデータ・壊れたデータ（参照切れ・重複）・原本の破損・途中での通信の切断・同じまとまりの二重送信で、§9.1 の失敗時の動作を検証する
- テストは偽サーバー（§2.3 段階 C）と、開発用のプロジェクト（承認後）の両方で行う。**テストには実在の個人情報を使わない**（デモデータ・合成データだけ）
