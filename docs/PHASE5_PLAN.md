# Phase 5 開発計画（案）— Phase 4 からの引き継ぎ

Phase 4 で、紙・PDFの書類を取り込み → 端末内で解析 → 確認 → 保存 → 在庫などへ再利用 する流れができた。
Phase 5 では、確認済みの書類を自動化エンジンにつなぎ、承認フローと照合を加える。

## 1. 最初に行うこと（検証）

| 項目 | 内容 |
| --- | --- |
| **実機 iPhone での検証** | カメラ撮影（`capture="environment"`）、写真ライブラリ・ファイルAppからの選択、HEIC、共有シートでのCSV保存、OCR の時間・メモリ・発熱、複数ページPDF、ホーム画面に追加した場合の保存領域。Phase 1〜4 を通じて未実施 |
| 実際の書類での精度評価 | 架空の書類を撮影した評価用データ（撮影条件を変えたもの）を作り、項目ごとの抽出率・誤り率を計測。現在はきれいな画面描画の書類でのみ確認 |
| 保存容量の上限確認 | iOS Safari の IndexedDB・Cache Storage の容量と、容量不足時の挙動 |

## 2. 自動化ルールの追加（Phase 4 の拡張点を使う）

Phase 4 の書類は `status: 'confirmed'` で確定し、項目は `fields`、明細は `lines` に正規化されている。これを `AutomationDefinition.detect()` の入力にする。

| 自動化 | 実行条件 | 実行内容 | 承認 |
| --- | --- | --- | --- |
| 納品書 → 入荷登録の提案 | 確認済みの納品書で、関連発注書が承認済み・在庫に未反映 | 明細と発注書の品目を照合し、入荷登録を提案（`receiveFromDocument`） | 要 |
| 請求書 → 支払タスク | 確認済みの請求書に支払期限がある | 期限の数日前を期限とする支払確認タスク | 自動可（タスクのみ） |
| 請求書と発注書・納品書の照合（三点照合） | 同じ取引先・書類番号の請求書・納品書・発注書がそろった | 数量・単価・金額の差異を表示し、差異がなければ「照合済み」 | 要 |
| 申請書 → 社員・入社準備 | 確認済みの申請書で関連社員がある | 内容に応じたタスク（備品申請 → 発注候補など） | 要 |
| 確認待ちの滞留 | 確認待ちのまま一定日数経過 | 担当者への確認タスク | 自動可 |

設計方針（Phase 3 の自動化エンジンと同じ）：判定は純粋関数、承認時にトランザクション内で再判定、結果は処理履歴に記録、外部への送信・発注・支払はしない。

## 3. 機能（優先度：中）

| 項目 | 内容 |
| --- | --- |
| 承認フロー | 書類・発注書・自動化提案の「申請 → 承認 → 確定」を共通化（承認者・差し戻し理由・期限） |
| 撮影の前処理 | 書類の輪郭検出・傾き補正・影の除去・二値化（OpenCV.js など無料のライブラリを必要時に読み込む。実機検証が前提） |
| 明細の表組み解析 | 罫線のある表・複数行の品名への対応（OCR の語の座標を使う） |
| 取引先マスタとの照合 | 発行元・登録番号から仕入先マスタの候補を提示し、`supplierId` に保存 |
| 抽出ルールの学習（ルールベース） | 利用者が修正した項目を集計し、ラベルの追加候補を提示（Phase 2 の分類ルール改善と同じ方式） |
| PWA 化 | Service Worker でアプリ本体もオフライン化（現在は OCR データのみオフライン可） |

## 4. 実運用に向けた基盤（変わらず必要）

認証・権限管理・複数ユーザーの同時利用・サーバー側のデータ保護・監査ログは未実装（デモ環境）。書類の原本を扱う場合は、保存期間（電子帳簿保存法など）・アクセス権・バックアップの方針を先に決める必要がある。外部への送信・有料サービスの利用は、オーナーの承認を得てから行う。
