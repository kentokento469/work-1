## 2. 保存の高速化（Phase 12 の残課題）

### 2.1 計測の方法

`e2e/perf.spec.ts`（`PERF=1` のときだけ実行）。Phase 12 と同じデータ（タスク・社員・問い合わせを IndexedDB に直接投入）で、クイック追加の保存を**3回行った中央値**と、その内訳を記録するようにした。

| 内訳 | 内容 |
| --- | --- |
| 書き込み | 操作の開始から、データベースへの書き込みの完了まで |
| 読み込み | 書き込みの後、画面のデータに反映するまで（改善前：全件の読み直し） |
| 再計算 | 統計・通知・自動化の提案・索引の計算 |
| 保存（合計） | 「追加」を押してから完了の通知が表示されるまで（描画を含む） |

内訳は、性能のテストが `window.__WC_PERF__` を設定したときだけ `performance.measure` で記録する（通常の利用では記録を溜めない）。テスト用の固定時計は `performance` も置き換えるため、性能のテストでは使わないようにした。

### 2.2 結果（ミリ秒。同じ環境で改善の前後を計測）

| 指標 | 10,000件 改善前 | 10,000件 改善後 | 50,000件 改善前 | 50,000件 改善後 |
| --- | --- | --- | --- | --- |
| **保存（合計）** | 1,033 | **408** | **4,329** | **1,101** |
| 　書き込み | 365 | 13 | 1,396 | 15 |
| 　読み込み | 249 | 26 | 1,349 | 41 |
| 　再計算 | 87 | 64 | 539 | 401 |
| 絞り込みの切り替え | 406 | 149 | 1,820 | 202 |
| 起動 | 567 | 543 | 2,233 | 1,957 |
| タスク一覧への移動 | 978 | 1,088 | 1,902 | 1,587 |
| 検索 | 786 | 1,002 | 1,279 | 1,581 |
| 画面の移動（3画面） | 1,070 | 803 | 1,349 | 898 |
| JS ヒープ | 21MB | 18MB | 105MB | 60MB |

- 50,000件の保存は **4.3秒 → 1.1秒（約 75% 短縮）**。10,000件は 1.0秒 → 0.4秒
- 1,000件（改善後）：保存 418ms・再計算 11ms
- 起動・一覧への移動・検索は今回の対象外で、差は計測のばらつきの範囲（同じ条件で数百ms 変動する。Phase 12 の記録ともずれがある）。今後の Phase で扱う
- 計測の数値は環境の負荷で変わる。前後の比較は、同じセッションで連続して計測したもの

### 2.3 原因と対策

CPU プロファイル（Chrome DevTools Protocol の Profiler）と内訳の計測で、原因を順に特定した。

| 原因 | 影響（50,000件） | 対策 |
| --- | --- | --- |
| **保存のたびに全データを読み直していた** | 読み込み 1.3秒 | **書き込みの記録（`ChangeTracker`）と差分の反映**（§2.4）。変わったデータの種類と id だけを読み直す |
| **自動化の自動実行が、保存のたびに全データを読み込んでいた** | IndexedDB の結果の復元（構造化複製）が約 0.5秒。プロファイルで idb の `success` が最大 | 画面が保持している最新のデータで判定する（実行する場合は、実行時にデータベースの内容で改めて判定する。既存の仕組み） |
| タスクの入力の検証で、全タスクを読んでいた（親・前提タスクの存在、循環の判定のため） | 書き込みの一部 | 検証に必要なタスクだけを読む：親・前提タスクとその先の前提（循環の判定）・自分のサブタスク。**DB v7** でタスクの親の索引（`byParent`）を追加し、サブタスクの検索・削除・完了でも全件を読まない |
| 書き込み中に、前の保存の後処理（通知の記録・自動化の判定）が重なっていた | 計測上の書き込み 0.3〜1.4秒（実際の書き込みは 16ms） | 上の2つと下の通知の記録の改善で、後処理そのものを短くした |
| 通知の記録の同期が、通知が変わらなくても毎回、大きな記録（期限超過の通知 約2.5万件）を読み込んでいた | 約 0.13秒 | 通知の内容（id・件名・種類）が前回と同じなら読まない |
| 通知の並べ替えで `localeCompare` を毎回呼んでいた | 約 0.1秒 | `Intl.Collator` を使い回す（順序は同じ） |
| 日数の計算（`diffDays`）が毎回 Date オブジェクトを2つ作っていた | 通知・統計で件数 × 回 | UTC の日付の通し番号の差で計算（タイムゾーン・夏時間の影響を受けない。4つのタイムゾーンの単体テストで確認） |
| メニューの項目ごとに通知を全件数え直していた | 約 50ms | 同じ通知の一覧への集計を `WeakMap` で1回にする |
| 自動化の判定で、提案の候補ごとに全タスクを探していた | 約 40ms | 作成済みのキーの集合をタスクの一覧ごとに1回だけ作る（`automation/taskKeys.ts`） |
| タスク一覧の範囲ごとの件数を、範囲の数（7）× 全件で数えていた・期限の比較で `localeCompare` | 絞り込み 1.8秒 | 1回の走査で全範囲を数える・`YYYY-MM-DD` は文字の比較 |

### 2.4 差分の反映の仕組み

```
サービス（変更なし）──書き込み──▶ Proxy で包んだ接続 ──▶ IndexedDB
                                    │ put/add/delete/clear・カーソルを記録
                                    ▼ トランザクションの完了時だけ確定
                              ChangeTracker { tasks: [id], activities: 'all', … }
                                    │ take()
AppData.refresh ──▶ loadChanges(前のデータ, 変更) ──▶ 変わった id だけ get ─▶ applyChanges
     │                                                         （並び順の位置に挿入・削除）
     └─▶ 別のタブへ変更（種類と id）を送る ─▶ 受け取ったタブも差分だけを読む
```

| 設計の判断 | 理由 |
| --- | --- |
| サービスの57か所の書き込みを書き換えず、接続を Proxy で包んで記録する | 変更の範囲を小さくし、記録の漏れを1か所の仕組みで防ぐ。代わりに、漏れがないことを単体テストで機械的に確認する（下） |
| id が分からない操作（全削除・カーソルでの削除）は、その種類を全件読み直す | 正しさを優先（操作履歴の上限の削除・復元など） |
| 記録はトランザクションの完了時だけ確定 | 入力の誤りなどで中断した書き込みを反映しない |
| 並び順を `sortSnapshot` の1か所で定義（主の条件が同じなら id の順） | 差分の反映と全件の読み込みが**同じ並び順**になる |
| 変わらなかった種類は同じ配列のまま | `WeakMap` によるキャッシュ（索引・集計）が効く。次の Phase の「変わった種類だけ再計算」の前提 |
| 反映は1つずつ順に実行 | 2つの反映が同じ古いデータから計算すると、片方の変更が消えるため |
| 差分の読み込みに失敗したら全件を読み直す | 安全側に倒す |

**検証**（`src/data/snapshotDelta.test.ts`）：タスクの作成・サブタスク・繰り返しの完了・サブタスクごとの削除、操作履歴の上限（カーソルでの削除）、入庫・出庫・問い合わせ・発注書の作成・社員の削除、復元（全削除と書き直し）、中断した書き込み、について、**操作のたびに「差分の反映 = 全件の読み直し」**と「変わらなかった種類は同じ配列のまま」を確認。

## 4. 残存課題（次の Phase 14 へ）

- 50,000件の保存は 1.1秒で、目標（1秒以内）に少し届かない。残りは再計算 0.4秒（通知 約0.13秒・ダッシュボード 約0.09秒・自動化の提案 約0.05〜0.09秒）とタスク一覧の再描画（並べ替え）
- **通知の過多**：期限超過のタスクが数万件あると、通知も数万件になる（利用者が読める量ではない）。集約（「ほか N件」）を、通知の設計（UX）とあわせて検討する
- 起動（50,000件で約2秒）・検索・一覧への移動は今回の対象外
- 実機での計測は未実施
