# WorkCore — 中小企業向け 統合業務管理・自動化アプリ

> 社内SE・バックオフィス業務の「属人化・転記・抜け漏れ」を減らすための業務管理Webアプリです。
> **Phase 1**：共通基盤・社員管理・入社準備の自動化
> **Phase 2**：社内ヘルプデスク・問い合わせ自動分類・FAQ提案・タスク連携・分析、Phase 1 の UX 改善
> **Phase 3**：在庫・備品・IT資産・購買管理、社員・ヘルプデスクとの連携、自動化エンジン（提案 → 承認 → 実行 → 履歴）
> **Phase 4**：書類管理（請求書・領収書・納品書・見積書・申請書）、端末内OCR・PDF解析、確認・修正、重複検出、CSV出力
> **Phase 6**：共通通知システム（通知センター・各画面の「要対応」・対象への直接移動と強調表示・未読と未処理の区別）、情報到達性の改善
> **Phase 5**：部門をまたぐ自動化ルールの一元管理（入社・退職・在庫・問い合わせ・書類）、スマート入力（電話番号・郵便番号→住所・金額・候補）、戻る操作の最適化（履歴・モーダル・スワイプ）

公開URL（GitHub Pages）: https://kentokento469.github.io/work-1/

> [!IMPORTANT]
> **これはデモ環境です。** GitHub Pages + ブラウザ内保存（IndexedDB）の構成で、データは**その端末のブラウザにのみ**保存されます。
> 複数端末でのデータ共有、ログイン認証、権限管理はありません。企業の本番システムとしては利用できません。
> 架空の企業「株式会社あおばテクノサービス」と架空の社員データのみを使用しています。
> 外部へのメール送信・実在アカウントの作成・外部申請は一切行いません（アプリ上でも同じ内容を表示しています）。
> 発注書はアプリ内の記録（下書き・承認・入荷）だけで、**外部への発注・メール送信・決済は行いません**。仕入先・在庫・資産もすべて架空です。
> 承認者名は自己申告の記録であり、本人確認はありません。在庫額は「参考単価 × 数量」の目安で、会計上の評価額ではありません。

## 1. 解決する業務課題

| 課題（中小企業のバックオフィス） | WorkCore の解決策 |
| --- | --- |
| 入社のたびに準備作業を記憶やExcelに頼る | 部署・雇用区分・入社日から**準備タスクを自動判定**（Phase 1） |
| IT・総務への問い合わせがチャット・口頭に散らばり、対応漏れが起きる | **問い合わせ番号で一元管理**し、状態・期限・担当・履歴を記録（Phase 2） |
| 問い合わせの振り分けに毎回判断が必要 | 本文から**カテゴリ・優先度を自動提案**（根拠付き、最終判断は担当者） |
| 同じ質問に毎回ゼロから回答している | **FAQ と過去の対応例を自動提示**、解決済み案件を確認付きで FAQ 化 |
| 問い合わせ対応の作業が担当者の頭の中だけにある | 問い合わせから**対応タスクを提案→承認→登録**し、タスク管理と連動 |
| 「対応した」と「申請者が納得した」の区別がない | **解決済み**と**完了**を分け、完了には申請者確認・全タスク完了を必須化 |
| 対応状況が見えない | 未対応・期限超過・平均解決時間・頻出問い合わせ・担当者別状況を**自動集計** |
| 備品・PCの在庫が Excel と記憶頼みで、入社直前に足りないと気付く | 入社予定者の部署から**必要機器を判定し、在庫を予約**。足りなければ**発注候補を自動作成**（Phase 3） |
| 在庫表・台帳・発注依頼書を何度も転記し、数が合わなくなる | **すべての数量変更を入出庫履歴に記録**し、在庫＝履歴の合計を常に検査。入荷1回で在庫・資産・発注書・予約を同時に更新 |
| 誰がどのPCを使っているか分からず、故障・退職時に探す | **IT資産台帳**（資産番号・利用者・状態・貸出履歴）。故障の問い合わせから**申請者の機器と代替機を自動で特定**、退職予定者の返却タスクを自動提案 |

## 2. 主な機能

### Phase 6（今回）
- **共通通知システム**：通知は実データから毎回作る（件数の保存・ダミー通知なし）。同じ原因からは1件だけ、対応が終われば自動で消え、削除された対象の通知は残らない。各通知に「何が起きたか・なぜ・何をすればよいか・発生日時・遷移先」を表示
- **ナビの件数の意味を統一**：すべて「未処理」（対応が終わるまで残る件数）。期限超過を含む時だけ赤、承認待ちは紫、未処理は紺、注意は黄。色だけでなくアイコンとラベルでも区別。問い合わせの二重計上を修正
- **原因がすぐ分かる**：タスク・問い合わせ・在庫・書類・入社準備の各画面の上部に「要対応 N件」（ナビの数字と同じ件数・同じ対象）。メニューの上部に「対応が必要な項目」と項目ごとの件数。ダッシュボードに「対応が必要なこと」
- **通知センター**（ヘッダーのベル・サイドバー）：未処理／未読／解消済み（履歴）を区別、機能・種類で絞り込み、すべて既読にする。既読にしても未処理の件数は減らない
- **対象への直接移動**：通知・リンクから対象の詳細画面へ。一覧の場合は対象までスクロールして控えめに強調表示し、絞り込みに隠れていれば解除して表示。自動化の提案は開いた状態で表示。詳細画面の上部に「なぜ表示されているか・何をするか」。対象が削除・処理済みなら案内を表示
- **関連情報**：タスクから対象社員の詳細へ（貸与機器・関連タスク・問い合わせ・書類）。入力中のダイアログが背景のデータ更新で消える不具合を修正

### Phase 5
- **横断自動化**：自動化センターにすべてのルールを一覧（実行条件・実行内容・有効/無効・実行方法）。社員登録 → 入社準備タスク、退職予定 → アカウント停止の確認・書類回収・社員証回収のタスク（アカウントの停止・削除は実行しない）、退職 → 機器返却、在庫不足 → 発注候補、問い合わせ → 申請者の過去の問い合わせ、書類 → 仕入先・社員・発注書の関連付け候補。新しいルールは `automation/registry.ts` に追加するだけで一覧・設定・履歴・二重実行防止が使える
- **実行方法の選択**：在庫・資産を変える操作は常に承認後に実行。タスクの作成だけを行うルールは「確認してから実行／自動で実行」を選べ、自動実行も処理履歴に記録・1回だけ。請求・発注・外部送信・申請・アカウント削除は自動化では実行しない
- **AI連携の設計**：分類・要約の差し替え口（`ai/assist.ts`）を用意。現在は**ルールベース（AIではありません）**と画面に表示し、設定画面に「AIモデル：未接続／外部への送信：なし」。ダッシュボードの「今日の要点」は自動集計
- **スマート入力**（共通部品 `ui/SmartInputs.tsx`）：電話番号（携帯・固定〔市外局番の桁数別〕・050・0120・0800 を自動でハイフン区切り、全角→半角、貼り付け、入力中はカーソルが動かない、電話番号キーボード）、郵便番号→住所（7桁で都道府県・市区町村・町域を補完、複数候補の選択、手で直した住所は上書きしない、取得できなくても手入力で続行）、メール（全角・大文字ドメインの正規化）、金額（全角・カンマ・「円」を除去、3桁区切り表示、不正な文字は注意）、役職・メーカー・単位・取引先の入力候補、社員の同姓同名の注意。日本語入力の変換中は値を書き換えない
- **戻る操作**：「一覧へ戻る」リンクは履歴を戻るので、検索条件・スクロール位置がそのまま。モーダルを開いた状態でブラウザの戻る・スワイプをすると、まずモーダルが閉じる（入力途中なら破棄確認）。Safari のタブでは標準のスワイプ戻りをそのまま使い、ホーム画面に追加して起動したときだけ画面左端からのスワイプで戻る（アプリ外には出ない・二重に戻らない・横スクロールや入力欄と競合しない）
- **データ**：IndexedDB v5（設定ストアを追加、既存データは自動移行）、社員に連絡先（電話・メール・住所）を追加、バックアップ v5（v1〜v4 も復元可）

### Phase 4
- **書類管理**：請求書・領収書・納品書・見積書・申請書・その他。一覧（処理状態のタブ・本文まで対象の検索・種類の絞り込み）、書類ID（DOC-年-連番）、登録/更新日時、処理状態（確認待ち・確認済み・保管済み）、抽出元（PDFテキスト／OCR／手入力）、関連業務
- **取り込み（iPhone 想定）**：カメラで撮影・写真から選ぶ・ファイル（PDF・画像）・手入力の4つの入口。取り込んだ時点で原本を端末に保存し、すぐに解析・確認へ。複数ページPDFは解析するページを選択。HEIC はブラウザが読める場合のみ（読めない場合は案内して手入力）
- **解析**：PDFに文字が埋め込まれていれば直接抽出し、文字のないページ・画像だけを OCR（Tesseract.js・日本語＋英語・Web Worker）。1ページずつ処理し、進行表示・キャンセル・失敗時の手入力への切り替えに対応。OCR のデータ（約8.6MB）は初回に利用者の操作でダウンロードし端末に保存（以後オフラインで利用可）。**画像は外部に送信しません**
- **項目の抽出**：書類名・発行日・発行元・宛先・書類番号・合計・税額・小計・登録番号（T＋13桁）・支払期限・納品日・申請者・申請内容・備考・明細（品名・数量・単価・金額）・税率別の税額。読めない項目は空欄のまま（推測で補わない）。値ごとに抽出元の行・確実性・理由を保存し、**OCR の文字認識の信頼度と、項目抽出の確実性を分けて表示**
- **確認・修正**：確認が必要な項目（重要項目・確実性が低い/中・形式や検算の注意）を先頭に表示。修正前の値・抽出元を参照、日付・金額・登録番号の形式チェック、小計＋税＝合計などの検算、一時保存と再開（入力途中も端末に自動保存）。発行元・発行日・合計金額は確認しないと「確認完了」にできない。スマホは「原本／項目」の切り替え、PCは左右に並べて表示
- **重複検出**：ファイル内容のハッシュ（完全一致）、発行元/登録番号＋書類番号（一致の可能性大）、発行元・登録番号・発行日・金額（類似）を区別し、比較画面で判断。自動で削除・統合しない
- **CSV出力**：一覧に表示中・選択・全件・期間と種類の指定。明細行は別ファイル。UTF-8 BOM・CSVインジェクション対策。iPhone では共有シート（「"ファイル"に保存」など）にも対応
- **Phase 1〜3 との連携**：社員・問い合わせ・発注書に書類を関連付け、各詳細画面に「関連書類」。納品書の明細は、確認済みの書類から利用者が品目と数量を確認して実行したときだけ在庫へ反映（入庫、または発注書の入荷として）。1つの書類から反映できるのは1回だけ
- **データ保護**：IndexedDB v4（書類と元ファイルを別ストアに保存、既存データは自動移行）。安全な削除（ゴミ箱 → 元に戻す／完全削除）。保存容量の表示と不足時の警告。バックアップ v4 に書類と元ファイル（任意）を含め、復元前に元ファイルのハッシュを検証

### Phase 3
- **在庫（数量管理）**：品目マスタ（ID・名称・カテゴリ・メーカー・型番・単位・最低在庫数・適正在庫数・参考単価・保管場所・仕入先・備考）、入庫・出庫・保管場所の移動・在庫調整（理由必須）・棚卸（入力途中を自動保存）、入出庫履歴、検索・絞り込み、在庫不足の表示、CSV
  - 数量は**実在庫・予約・利用可能・入荷待ち需要・発注残**を区別。出庫は利用可能数まで。在庫を直接書き換えず、取り消しも逆向きの記録を追加
- **IT資産台帳（1台ずつ管理）**：PC・スマートフォンを資産番号（AST-0001〜）で管理。状態（未使用・予約済み・使用中・修理中・故障・廃棄予定・廃棄済み）、利用者、貸出・返却・状態変更の履歴。同じ機器を2人に貸し出せない
- **購買支援**：在庫不足から**発注候補（下書き）を自動作成**（推奨数量・概算金額・判定の根拠）→ 仕入先ごとに発注書（下書き）→ 承認申請 → 承認 → 入荷登録（一部入荷可）→ 在庫・資産に反映。仕入先マスタ、発注依頼書の印刷
- **社員との連携**：入社予定者の部署から必要機器を判定 → 在庫を予約（不足分は入荷待ち＋発注候補）→ 準備タスク。入社日・部署の変更、入社取り消し、退職予定者の返却タスクに対応。社員詳細に貸与機器を表示
- **ヘルプデスクとの連携**：故障の問い合わせ → 申請者の使用中機器を特定 → 未使用の代替機を提案（なければ入荷待ち）→ 承認で修理中・代替機の貸出・タスク。問い合わせ詳細に関連機器を表示
- **自動化センター**：上記の提案を一覧し、実行条件（根拠）・実行内容を確認して承認／見送り。在庫・資産を変える操作は**承認するまで実行されない**。実行・見送り・失敗を処理履歴に記録
- **在庫分析**：総在庫・利用可能数・貸与中の機器・不足品目・入荷待ち、月別の入出庫、カテゴリ別の参考在庫額、資産の使用状況、故障・交換履歴、仕入先別の発注額（参考単価・取得価額・会計評価の違いを明記）
- **ダッシュボード**：在庫不足・発注候補・承認待ち・入荷待ち・貸与中の機器、承認待ちの自動化提案

### Phase 2
- **ヘルプデスク**：問い合わせの登録・編集・削除（取り消し可）・検索、`HD-年-連番` の自動採番、受付日時、申請者（社員マスタから選択・部署は自動）、カテゴリ、優先度、担当者、期限（カテゴリの標準日数から自動計算）、ステータス（新規／対応中／回答待ち／保留／解決済み／完了）、コメント・対応履歴、解決内容、完了日時
- **自動分類（ルールベース）**：キーワードの最長一致＋加点方式でカテゴリ・優先度を提案。根拠（一致語・点数・加点理由）を表示。根拠が弱い・拮抗する場合は「その他・要確認」。「ログインできない」だけでは高優先度にしない
- **FAQ・解決策提案**：FAQ の登録・編集・削除・有効/無効、カテゴリ・キーワード検索、関連 FAQ 候補、過去の対応例（**未検証の参考情報**として FAQ と明確に区別）、問い合わせとの関連付け、解決済み案件からの FAQ 化（一般化・秘密情報除去の確認が必須）
- **タスク連携**：問い合わせ内容から対応タスクを提案 → 担当者が選択・調整して承認 → タスク管理に登録。同じ問い合わせからの重複作成を防止。タスクの状態変化は問い合わせの対応履歴に反映（問い合わせは自動では閉じない）
- **分析**：未対応・対応中・解決済み・期限超過、カテゴリ別・優先度別件数、平均・中央値の解決時間（定義を明示）、頻出問い合わせ、担当者別状況、自動分類の採用率。件数不足の指標は「データ不足」と表示
- **秘密情報の保護**：パスワード・認証コード・カード番号らしき文字列を検出し、保存をブロック（ワンタップで伏せ字化）。操作履歴には本文・コメントを書かない
- **カテゴリ管理**：カテゴリの追加・編集・無効化、分類キーワード・既定担当者・標準対応日数の設定

### Phase 1 の UX 改善（監査結果に基づく。詳細は [docs/UX_AUDIT.md](docs/UX_AUDIT.md)）
- 一覧の検索条件を URL に保存（詳細から戻っても保持）、スクロール位置の復元
- 入力中のフォームを誤って閉じても消えない（変更がある時だけ破棄確認）、問い合わせの下書き自動保存
- 削除・ステータス変更を通知の「元に戻す」で取り消し可能（タスク削除の確認ダイアログを廃止）
- タッチ領域 44px 以上、通知をスマホでは親指の届く下部に表示、スマホではフィルターを折りたたみ
- 画面の遅延読み込み＋先読みで初回 JS を 129KB → 101KB（gzip）に削減

### Phase 1（既存）
ダッシュボード（部署別社員数は在籍中・入社予定・退職予定・休職中・退職済の積み上げバーと凡例・内訳で表示）、社員管理（重複防止つき）、入社準備の自動化（プレビュー→登録・重複防止・ルール編集）、タスク管理、CSV（Excel 対応 UTF-8 BOM）・JSON バックアップ／復元・操作履歴・デモデータ。

## 3. システム構成（概要）

```
UI層 (React + Tailwind)        pages/ features/ ui/   … 表示と入力のみ
状態管理                        app/AppData.tsx        … run(): 実行→再読込→通知(元に戻す)
サービス層                      services/              … 検証→保存→履歴 を1トランザクションで実行
  WorkCoreService (社員・タスク・入社準備・データ)  /  HelpdeskService (問い合わせ・FAQ・カテゴリ)
  InventoryService (在庫・資産・発注・自動化提案の実行)
  DocumentService (書類の登録・抽出結果の反映・確認・ゴミ箱)
ドメイン層 (純粋関数・UI非依存)  domain/ automation/    … 分類・検索・提案・在庫計算・書類の項目抽出・重複検出・集計・検証
自動化エンジン (UI非依存)        automation/engine.ts   … 判定(detect) → 提案 → 承認時に再判定して実行 → 処理履歴
書類解析 (ブラウザ内)            features/documents/engine … PDF.js・Tesseract.js を必要時に読み込み、1ページずつ処理
永続化層                        data/db.ts (IndexedDB v5) / backup.ts (v1〜v5互換) / csv.ts
戻る操作                        app/router.ts (履歴の位置・モーダル) / app/swipeBack.ts (単独起動時のスワイプ)
```

詳細は [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)。

### 技術選定
| 技術 | 理由 |
| --- | --- |
| React 18 + TypeScript（strict, `noUncheckedIndexedAccess`） | 業務データの型安全性 |
| Vite / Tailwind CSS v4 | 静的ファイル出力で GitHub Pages に配置可能・デザイントークンの一元管理 |
| IndexedDB（`idb`） | 無料・サーバー不要で永続化。トランザクションと一意インデックスで整合性を確保 |
| 外部AIなしのルールベース分類 | 無料・オフライン動作・判定根拠を説明できる（Phase 2 の要件） |
| Vitest + fake-indexeddb / Playwright | ロジックとDB処理は単体テスト、画面は iPhone 13 相当と PC で E2E |
| PDF.js 5.4（legacy ビルド） | PDF の表示と埋め込みテキストの抽出をブラウザ内で行う。古い iOS Safari も考慮して legacy ビルドを使用 |
| Tesseract.js 7（日本語＋英語の best_int モデル） | 無料・オープンソース・ブラウザ内（Web Worker）で動く OCR。画像を外部に送らない。モデルは小容量版（計約5MB）を自サイトから配信 |
| libphonenumber-js（最小メタデータ） | 電話番号の市外局番ごとの区切り。入力欄を使うときだけ読み込む |
| jp-postal（日本郵便 KEN_ALL） | ビルド時に先頭3桁ごとの JSON に変換し、自サイトから配信（住所検索で外部に送信しない） |
| Cache Storage | OCR エンジン・言語データを初回だけダウンロードして保存し、オフラインでも OCR を使えるようにする |

## 4. 面接での実演手順（スマートフォン）

### Phase 6（通知・情報到達性）
1. 下部ナビ「タスク」の数字を確認 → タップ → 画面上部の「要対応」に同じ件数の期限超過タスクと理由が並ぶ → その場でステータスを「完了」→ ナビの数字が1減る
2. 「メニュー」→ 上部の「対応が必要な項目」と、項目ごとの件数（書類・自動化センター・入社準備）
3. ヘッダーのベル → 通知センター（未処理・未読・解消済み）→ 通知を押すと対象へ移動して強調表示 → 戻ると通知センターの絞り込みがそのまま

### Phase 5（横断自動化・スマート入力・戻る操作）
1. 「メニュー」→「社員管理」→「新規登録」→「連絡先・住所」を開き、電話番号に `0466123456` → 欄を離れると `0466-12-3456`。郵便番号に `2540822` → 住所が入る
2. 「登録する」→「自動化センター」に入社準備タスクの提案 → 開いて「承認して実行」（連打しても1回だけ）
3. 自動化センターの「自動化ルールの設定」で入社準備タスクを「自動で実行」にすると、次の登録から自動で作成される
4. 社員一覧で部署を絞り込み → 社員を開く → 画面左端からスワイプ（Safari）または「社員一覧」で戻ると、絞り込みとスクロール位置がそのまま
5. 「新規登録」で氏名を入力した状態でスワイプ／戻る → 閉じずに「入力した内容は保存されていません」

### Phase 4（書類処理）
1. 「ホーム」の書類カードの「取り込む」（またはメニュー →「書類管理」→「取り込む」）
2. 「カメラで撮影」で紙の領収書を撮影（または「写真から選ぶ」「ファイルを選ぶ」で PDF）
3. 初回のみ「OCRを準備する（約8.6MB）」→「解析を開始」→ 進行状況を確認
4. 「確認が必要な項目」で、抽出元の行・確実性を見ながら修正 →「原本」タブで原本と照合 → 重要項目にチェック →「確認完了」
5. 同じ写真をもう一度取り込むと「同じファイルが既に登録されています」と警告
6. 納品書なら「明細を在庫に反映する」→ 品目と数量を確認 →「在庫に反映する」
7. 書類一覧の「CSV出力」で期間・種類を指定して出力


### Phase 3（在庫・資産・購買）
1. 下部ナビ「メニュー」→「社員管理」→「新規登録」で入社予定者を登録（部署・入社日を入力）
2. 「ホーム」の「承認待ちの自動化提案」→ 登録した社員の「入社準備機器」を開く → 実行条件（必要機器・在庫）と実行内容を確認 →「承認して実行」
3. 下部ナビ「在庫」→ ノートPC・マウスの**利用可能数が減った**（実在庫は同じ＝予約）ことを確認
4. 「発注」タブ → 自動作成された**発注候補**（推奨数量・根拠）→「発注書（下書き）を作成」→ 承認申請 → 承認者を入力して承認 →「入荷を登録」→ 在庫・資産に反映
5. 「IT資産」タブ → 未使用のPCを「貸出」→「返却」→ 資産の履歴を確認
6. 問い合わせで「ノートPCが故障して起動しない」を登録 → 詳細画面の**関連機器**で代替機の提案を承認
7. 「自動化センター」で退職予定者の返却タスク提案、処理履歴を確認

### Phase 2（ヘルプデスク）

1. ダッシュボードの「ガイドを始める」をタップ（以降、操作に応じて自動でチェックが付きます）
2. 下部ナビ「問い合わせ」→「問い合わせを登録」
3. 申請者を選択 → 件名「新入社員のPCが足りません」と入力 → **自動分類**（PC・周辺機器）と担当者・期限の自動入力、「判定の根拠を見る」を確認
4. 「受け付ける」→ 詳細画面の「次にやること：対応タスクを作成」→ 提案（在庫確認・発注・入社準備との照合）を確認・調整 →「承認して登録」
5. 対応タスクのステータスを「完了」に → 対応履歴に反映されることを確認
6. 「解決済み」→ 解決内容を記録 →「完了にする」（申請者確認のチェック）
7. ヘルプデスクの「分析」で集計を確認、「FAQにする」で FAQ 化
8. 補足デモ：「ログインできない」→ その他・要確認（過剰判定しない）、「パスワード: xxx」→ 保存ブロックと伏せ字化

## 6. 開発・公開

```bash
npm install
npm run dev          # 開発サーバー（OCR・PDF処理のファイルのコピーと郵便番号データの生成を public/vendor/ に自動で行う）
npm run typecheck    # 型チェック
npm test             # 単体・結合テスト
npm run build        # 本番ビルド（dist/）
npm run test:e2e     # E2E（Chromium のパスは CHROMIUM_PATH で指定可）
```

`main` への push で GitHub Actions が型チェック・テスト・ビルド後に GitHub Pages へ公開します（Settings → Pages → Source を「GitHub Actions」に設定済み）。

既存ユーザーのデータは保持されます：初回起動時に IndexedDB が最新版（v5）へ自動移行し（在庫は空、保管場所・仕入先マスタのみ追加）、Phase 1・2 のバックアップ（schemaVersion 1・2）もそのまま復元できます。既存データに在庫のデモだけ追加したい場合は「データ管理 → 在庫のデモデータを追加」、ヘルプデスクのデモは「ヘルプデスクのデモデータだけ追加」を使います。

## 8. 制約・未実装（Phase 6 時点）
- 通知はこの端末のブラウザ内のデータから作ります。プッシュ通知（アプリを閉じている間の通知）や、複数端末・複数ユーザーでの既読の共有はありません
- **iPhone 実機では未検証**：Safari 標準のスワイプ戻り、ホーム画面から起動した単独表示モードでの独自スワイプ、日本語キーボードでの入力補助は Chromium のエミュレーションでのみ確認
- AI モデルは接続していません（分類・要約はルールベースで、画面にもそう表示）。外部AIサービスへの送信は行いません
- 電話番号は形式の整形のみで実在は確認しません。郵便番号データは KEN_ALL（事業所の個別番号は含まない）
- 社員の連絡先（電話・住所）は端末のブラウザ内に保存されます。閲覧権限の管理はありません（デモ環境）
- OCR は端末内で動作するオープンソースの Tesseract.js（無料・外部送信なし）。撮影条件・手書き・複雑な表では精度が下がるため、**必ず確認画面で原本と照合**してください。登録番号の実在確認（国税庁への照会）は行いません
- 書類の元ファイルは端末のブラウザ内に保存されます。容量には上限があり、ブラウザのデータ削除で消えるため、元ファイル込みのバックアップを推奨します
- **本番企業向けの認証・権限管理、複数ユーザーの同時利用、サーバー側のデータ保護はありません。** 1台のブラウザ内での連打・二重送信はトランザクションと冪等キーで防ぎますが、複数端末・複数ユーザー間の整合性は保証しません
- 外部への発注・メール送信・決済・外部AIは使用しません（発注書は印刷できるアプリ内の記録のみ）
- 在庫額は参考単価による目安で、会計上の評価（取得原価・減価償却・低価法など）ではありません
- 機器ルール（入社時に必要な機器）は初期設定を使用し、編集画面は未実装（Phase 4）。バーコード読み取り・安全在庫の自動計算は未実装
- 認証・権限・複数端末同期なし（デモ環境）。申請者本人による問い合わせ投稿画面（セルフサービス窓口）は未実装で、担当者が代理登録する前提
- 自動分類はキーワード規則のため、否定表現（「〜ではない」）や文脈は解釈しない。判定は必ず担当者が確認する
- 解決時間は暦時間（夜間・休日を含む）。営業時間ベースの SLA 計測は未対応
- 祝日は期限計算に未考慮（土日のみ）
- サイドバーの「今後追加予定」モジュールは表示のみ（「準備中」と明示）
