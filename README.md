# WorkCore — 中小企業向け 統合業務管理・自動化アプリ

> 社内SE・バックオフィス業務の「属人化・転記・抜け漏れ」をなくすための業務管理Webアプリです。
> **Phase 1** として、共通基盤と「人事・入社準備の自動化」を実装しています。

- 架空企業「株式会社あおばテクノサービス」のデモデータ入り（実在の人物・企業とは無関係）
- サーバー不要・無料で動作（データはブラウザの IndexedDB に保存、外部送信なし）
- iPhone Safari を最優先に設計したレスポンシブUI／ダークモード対応

---

## 1. 開発目的と解決する業務課題

| よくある課題（中小企業のバックオフィス） | WorkCore での解決 |
| --- | --- |
| 入社のたびに「何を準備するか」を担当者の記憶やExcelに頼っている | 部署・雇用区分・入社日から**準備タスクを自動判定**し、期限も自動計算 |
| 情シス・人事・総務の作業が分散し、進捗が見えない | タスクを担当部署・担当者・期限で一元管理、**ダッシュボードで即時集計** |
| 同じ依頼を二重に出す／漏らす | 同一社員への**同一タスク重複生成を自動防止**、社員番号の重複も防止 |
| 期限切れに気づくのが遅い | 期限超過・期限間近・準備未着手を**優先対応リストに自動抽出** |
| 部署ごとに必要な準備が違い、変更に追従できない | 準備ルールを**画面から追加・編集・無効化**でき、次回生成から反映 |
| データがExcelに散らばる | CSV（Excel対応）出力、JSONバックアップ／検証付き復元 |

将来的に以下の5モジュールを統合する計画です（Phase 1 は①と共通基盤）。

1. 人事・入退社・アカウント管理 ← **Phase 1**
2. 社内ヘルプデスク
3. 請求書・領収書処理自動化
4. 在庫・発注管理
5. 業務ワークフロー自動化

## 2. 機能一覧（Phase 1 実装済み）

### A. ダッシュボード
- 統計カード：登録社員数（退職者除く）／入社予定者数／未完了タスク／期限超過／タスク完了率
- **優先対応が必要な業務**：期限超過 → 期限間近（3日以内・優先度中以上）→ 入社30日以内でタスク未生成の社員、を自動抽出・並べ替え
- タスク進捗（ステータス別積み上げバー＋件数・割合、タップで絞り込み）
- 部署別社員数（横棒グラフ、タップで社員一覧を絞り込み）
- 入社予定者ごとの準備進捗バー、最近の操作履歴
- すべての数値は保存直後に再集計され、即時反映

### B. 社員管理
- 一覧（スマホ：カード／PC：テーブル）・詳細・新規登録・編集・削除
- キーワード検索（氏名・社員番号・役職・備考・部署、空白無視）、部署／ステータスフィルター
- 管理項目：社員番号・氏名・所属部署・役職・雇用区分・入社日・退職日・在籍ステータス・備考
- **社員番号の重複防止**：入力中に即時警告＋サービス層で検証＋IndexedDB の一意インデックス（全角・大小文字を正規化して比較）
- 入社日・退職日からステータスを自動提案、退職日の前後関係などの入力検証
- 削除時は関連タスク件数を明示し、同時に削除（孤立データを残さない）

### C. 入社準備自動化
- 社員を選ぶと **共通ルール＋所属部署ルール** を判定し、雇用区分による対象外も判定
- 期限 = 入社日 ± N日 → 土日なら直前の平日 → 既に過ぎていれば本日、の順に自動計算
- **登録前プレビュー**：チェックで取捨選択、担当者・期限・優先度をその場で変更可能
- 登録済み（同一ルール／同名タスク）は「登録済み」、対象外は理由付きで表示
- 登録時はトランザクション内で再判定するため、プレビュー後の変更があっても重複しない
- 新入社員の登録直後に「入社準備タスクを生成しますか？」と案内
- **準備ルール設定**：追加・編集・削除・有効/無効、適用範囲（共通／部署）、担当部署、既定担当者、優先度、期限日数、対象雇用区分
- 部署マスタの追加・名称変更・削除（使用中の部署は削除不可）

### D. タスク管理
- 新規作成・編集・削除、未着手／進行中／完了／保留
- 優先度・担当部署・担当者・期限・対象社員の紐付け
- 一覧からワンタップでステータス変更（iPhone ではネイティブピッカー）
- 期限超過は赤帯＋超過日数、期限間近は残日数を表示
- ステータスタブ（件数付き）、優先度／担当部署／対象社員／キーワード絞り込み、期限・優先度・更新順の並び替え
- 完了日時の自動記録（完了を戻すとクリア）

### E. データ管理
- IndexedDB への永続保存（再読み込み・再訪問後も保持）
- CSV エクスポート（社員・タスク）：**UTF-8 BOM＋CRLF** で Excel でも文字化けしない／CSVインジェクション対策
- JSON バックアップ／**復元**：アプリID・スキーマバージョン・全レコードの型・ID重複・参照整合性（部署・社員の存在）を検証し、件数の増減を示して上書き確認
- 操作履歴（最大300件、種類で絞り込み）
- デモデータの初期化・再生成、全削除（空の状態から開始）

```
│        │                                                                             │

│   domain/analytics.ts（集計）      │   tasks・rules・activities・meta                   │

│   data/backup.ts・csv.ts          │                                                  │
└───────────────────────────────────────────────────────────────────────────────────┘
```

### 自動化エンジンの処理フロー

```
社員を登録 → 部署・雇用区分・入社日を判定 → 適用ルールを抽出 → 期限を計算（休日・過去日補正）
          → 既存タスクと重複チェック → プレビュー（利用者が確認・調整）→ タスク登録 → ダッシュボード反映
```

`buildOnboardingPlan()`（計画作成）と `materializePlan()`（タスク化）は入出力がプレーンなデータの純粋関数です。
「計画」を保存すれば承認フローに、外部へ送れば API 連携（アカウント発行システム等）に拡張できます。

### ディレクトリ

```
src/
  domain/       型定義・日付・検証・集計（純粋関数）
  automation/   入社準備自動化エンジン
  data/         IndexedDB スキーマ、CSV、バックアップ検証
  services/     アプリケーションサービス（トランザクション・操作履歴）
  demo/         架空企業のデモデータ生成
  app/          ルーター・テーマ・状態管理・レイアウト
  ui/ features/ pages/   画面
e2e/            Playwright による業務シナリオテスト
```

## 4. 技術選定理由

| 技術 | 理由 |
| --- | --- |
| React 18 + TypeScript（strict, `noUncheckedIndexedAccess`） | 型で業務データの整合性を担保。採用市場で一般的 |
| Vite | 高速ビルド、静的ファイル出力で GitHub Pages に載せやすい |
| Tailwind CSS v4 | デザイントークン（ネイビー系パレット・ダークモード）を一元管理 |
| IndexedDB（`idb`） | サーバー不要・無料で永続化。トランザクションと一意インデックスで整合性を確保。localStorage より容量・構造面で有利 |
| Lucide Icons | 業務SaaS向けの統一されたアイコン |
| 自作の軽量グラフ（CSS/SVG） | 必要なグラフは3種類のみ。ライブラリ追加より軽量（JS 約88KB gzip） |
| ハッシュルーティング（自作） | GitHub Pages はサーバー側リライト不可のため `#/path` 方式 |
| Vitest + fake-indexeddb / Playwright | ロジックは実DB相当で単体テスト、画面は iPhone 13 相当とPCでE2Eテスト |

外部AI API・有料サービスは使用していません。

## 5. 設計上の重要な判断（面接向けサマリー）

1. **業務ロジックをUIから分離** — 自動化エンジン・集計・検証は React に依存しない純粋関数。テスト容易性と、将来のサーバー移行・API化を見据えた構成。
2. **重複防止を三重に** — ①入力中の即時警告 ②サービス層での検証 ③DBの一意インデックス。入社タスクは「ルールID」と「正規化したタスク名」の両方で重複判定。
3. **プレビュー → 確定の2段階** — 自動化の結果を人が確認・調整してから登録。確定時はトランザクション内で再計算し、プレビュー後の変更による二重登録を防止。
4. **ルールをデータとして持つ** — 部署別の準備内容をコードに埋め込まず、画面から変更可能に。変更は次回生成から反映し、登録済みタスク（業務記録）は変えない。
5. **書き込み＝検証＋保存＋操作履歴を1トランザクション** — 途中失敗で中途半端なデータが残らない。社員削除は関連タスクも同時に削除。
6. **外部データは信用しない** — 復元ファイルは型・ID重複・参照整合性まで検証し、問題があれば現在データを一切変更しない。
7. **デモデータは「今日」基準で生成** — いつ開いても入社予定・期限超過などの状態を体験できる。
8. **スマホ最優先** — 下部ナビ、44px以上のタップ領域、ボトムシート型モーダル、16px入力（iOSズーム防止）、セーフエリア対応、横スクロールなし（E2Eで検証）。

## 6. 操作方法

### 基本の流れ（デモ）
1. **ダッシュボード**で「優先対応が必要な業務」を確認
2. **社員** → 「新規登録」で入社予定者を登録（社員番号は自動提案）
3. 登録後の案内から **入社準備**のプレビューへ → 内容を確認・調整 → 「◯件のタスクを登録する」
4. **タスク**で担当者・期限を編集、右側のステータスから「完了」に変更
5. ダッシュボードの数値が即時に変わることを確認
6. **データ** → CSV出力／JSONバックアップ／復元、デモデータの初期化

### ローカル開発

```bash
npm install          # 依存関係（.npmrc で legacy-peer-deps を有効化）
npm run dev          # 開発サーバー
npm run typecheck    # TypeScript チェック
npm test             # 単体・結合テスト（Vitest）
npm run build        # 本番ビルド（dist/）
npm run test:e2e     # E2E（Playwright。Chromium のパスは CHROMIUM_PATH で指定可）
```

## 7. 動作確認結果（2026-10-15 実施）

| 確認項目 | 方法 | 結果 |
| --- | --- | --- |
| TypeScript チェック（strict） | `npm run typecheck` | ✅ エラー 0 |
| 本番ビルド | `npm run build` | ✅ JS 295KB（gzip 88KB）/ CSS 51KB |
| 単体・結合テスト | Vitest（26件） | ✅ 26/26 合格 |
| 業務シナリオ E2E | Playwright（iPhone 13 相当・デスクトップ × 2シナリオ） | ✅ 4/4 合格 |
| 依存パッケージ脆弱性 | `npm audit` | ✅ 0件 |

E2E で検証した業務フロー（指定の10項目）：

1. 新入社員を登録（重複社員番号の警告も確認）
2. 入社準備タスクを自動生成（営業部：共通7件＋部署2件、1件を選択解除して8件登録、再生成で重複しないことを確認）
3. タスクを編集（担当者・優先度）
4. タスクを完了
5. ダッシュボード更新を確認（入社予定者+1、未完了+7、操作履歴）
6. 社員情報を検索（氏名・社員番号・部署フィルター）
7. CSV出力（BOM付きUTF-8・内容を検証）
8. JSONバックアップ
9. バックアップ復元（不正ファイルの拒否、上書き確認）
10. 再読み込み後のデータ保持（編集内容・完了状態まで保持）

加えて、ナビゲーション・ダークモード切替・必須入力エラー表示・**スマホ幅での横スクロールなし**を確認しています。
※ 実機 iPhone Safari での確認は GitHub Pages 公開後に実施が必要です（本検証は Chromium による iPhone 13 エミュレーション）。

## 8. GitHub Pages 公開手順

`.github/workflows/deploy.yml` を同梱済みです（型チェック・テスト・ビルド後に公開）。

1. このリポジトリを GitHub に push
2. GitHub のリポジトリ画面 → **Settings → Pages → Build and deployment → Source** を **GitHub Actions** に変更
3. Actions タブで「Deploy to GitHub Pages」が成功すると `https://<ユーザー名>.github.io/<リポジトリ名>/` で公開
4. iPhone Safari で開き、共有メニュー →「ホーム画面に追加」でアプリのように利用可能

> データは端末ごとのブラウザに保存されます。端末間で共有する場合は JSON バックアップ／復元を使ってください。
> プライベートブラウズでは保存が制限される場合があります。
